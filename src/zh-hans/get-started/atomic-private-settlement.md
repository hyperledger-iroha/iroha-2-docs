# 运行原子私有跨数据空间的金融交易结算 {#run-atomic-private-cross-dataspace-settlement}

`AtomicPrivateSettlementV1` 在 2 到 255 个 SORA Nexus 数据空间中协调每个机密财务转账部分，并在一个全局状态中完成每个财务转账部分交易。被拒绝、过期或中止的捆绑不适用任何财务转移部分。透明原生 AMX DvP/PvP 仍然是一个独立的协议路径。

::: warning 发布状态
此功能受限，默认禁用，尚未经过生产环境验证。在发布功能之前，请勿为真实 CBDC 值启用它，隐私、故障、性能、可重现构建、独立加密审查和工件发布关卡都已通过该确切版本的测试。
:::

## 协议隐藏的内容 {#what-the-protocol-hides}

每个金融转账部分使用固定的双输入、三输出私有记证明。委员会验证者验证该证明和不透明的状态变更；他们不会接收到明文的交易方、资产、金额、备注或业务结果。授权的本地审计员解密带填充的审计胶囊，检查其内容，并签署目的分离的批准。默认策略接受来自受管理审计员集合的一个批准。

公共容器交易和协议结果记录故意显示：

- 网络和捆绑标识符
- 参与者数据空间路由和参与者数量
- 时机和到期高度
- 稳定的不透明协议数据组标识符、根、作废者、加密承诺值和固定密文槽
- 委员会授权原则和确切的3-4可用性，准备以及协议最终化证书
- 赞助商、公共网络费用和终端状态

这是内容保密，而不是流量匿名。时间、参与者数量、数据空间身份和稳定池活动仍然是公开的。一个只托管一个 CBDC 的数据空间，即使没有发布字面资产标识，也可能从路线推断出该资产。

每个固定加密输出都发布一个`recipient`标识符，该标识符源自其授权的一次性输出视图密钥。一个金融传输部分中的三个标识符必须是不同的;完整的Prepare屏障和协议结果记录将该检查扩展到所有金融传输部分。在投票准备之前，每个委员会验证者也会拒绝已经出现在已最终确定的 WSV 中的标识符。全球最终确定在已最终确定的捆绑历史中执行相同的规则，并使用确定性的接收者索引。该索引在即时数据视图负载中被排除，并在恢复期间从单个协议标准加密输出重建，因此已保存的重复项会失败关闭。这是一次性标识符和重放边界，并不保证恶意发送者或网络观察者在发布前无法关联流量。

## 部署要求 {#deployment-requirements}

在激活之前，操作员需要以下所有内容：

1. 每个参与的数据空间恰好有四个验证者，拥有不同的 BLS 共识密钥和持有证明
2. 每个高度都启用强制 Sumeragi DA/RBC
3. 每个数据空间中的受管理机密财务交易结算协议数据组和初始根
4. 一个活跃的 V1 私人笔记功能以及独立的金融交易结算证明档案
5. 至少一个受管理的本地 `PrivateSettlementAuditPolicyV1`，包括不同的审计员签名和混合加密密钥、密钥周期、高度有效性以及批准阈值
6. 为配置的保留期提供足够的私有辅助记录存储
7. 能够提交最终公共容器交易的中立赞助商账户

审计员也可以操作验证器，但必须使用独立的共识密钥、审计员签名密钥和审计员加密密钥。在退役解密密钥时，应保留至法规规定的保留期，或在退役之前管理并测试胶囊重新封装。

四验证器授权原则是由状态锚定的，而不是由客户端提供的。在技术清单的 `authority_context_height` 处，每个验证器都会从共识状态解析出精确的有序通道/数据空间名册和活跃执行通道实例，并要求解析出的高度匹配，并验证四个 BLS 密钥和持有证明。上传、准备以及最终协议结果记录的审批都使用相同的历史授权原则。

准备屏障、最终协议定稿包和协议结果记录共享一个紧凑的两级授权主体目录。其 `rosters` 包含无路径验证器身份和对齐的 BLS 持有证明，在单一协议标准的首次使用顺序中去重。`leg_roster_indices[i]` 选择技术清单财务转移部分的花名册 `i`。阶段证书的 `authority_catalog_index` 保持逻辑清单顺序号，而不是花名册索引。在权威摘要或 QC 验证之前，验证者将该技术性展示的财务转移部分的精确路径和活动执行通道实例与所选名册结合起来，以重建路径绑定的 `PrivateSettlementCommitteeAuthorityV1`。

## 配置入场 {#configure-admission}

所有生产行为都来源于节点配置。环境变量无法激活此路径。默认随附值为 `enabled = false`；保持功能禁用无需特定结算配置。

在治理注册了所需的能力并选择了适当通知后的激活高度后，一致地配置每个相关节点：

```toml
[nexus.atomic_private_settlement]
enabled = true
activation_height = 500000
minimum_activation_notice_blocks = 7200
proof_profile_version = 1
max_participants = 255
max_expiry_blocks = 7200
audit_timeout_blocks = 1200
prepare_timeout_blocks = 1200
commit_timeout_blocks = 1200
capsule_padding_classes_bytes = [4096, 16384, 65536, 262144]
max_proof_bytes = 8388608
max_capsule_bytes = 1048576
max_carrier_bytes = 4194304
sidecar_retention_blocks = 1000000
sidecar_max_records = 256
sidecar_max_total_bytes = 3221225472
default_min_auditor_approvals = 1
permitted_policy_versions = [1]
```

该示例使用了随附的 V1 限制，而不是性能建议。请测量存储、证明、胶囊、容器事务以及延迟数据容器的情况。在选择操作范围之前，需要考虑预期的硬件。三个阶段的超时必须适合`max_expiry_blocks`，辅助记录保留时间必须至少达到该过期窗口。

`max_capsule_bytes` 限制了整个 `PrivateSettlementAuditCapsuleV1` 的单一协议标准 Norito 编码：AAD、加密随机数值、密文、向量帧、审计员身份，以及每一行封装的 DEK。它不是仅针对密文的限制。每个配置的填充类必须至少适合 `default_min_auditor_approvals` 名审计员使用的保守全胶囊数据容器。 Torii 也拒绝了一个新的已承认的策略，其`min_approvals`低于规定的下限，并且拒绝任何完整单一协议标准编码过大的实际胶囊。

`max_carrier_bytes` 限制完整的单一协议标准的赞助商签署交易，而不仅仅是认证捆绑包。计数包括已注册的指令框架、交易授权主体和元数据、费用意图以及签名。常规网络交易限制仍然适用，作为独立的上限。

除非被管理的能力处于激活状态，其状态和激活高度满足通知期，编译的证明配置文件匹配 V1，并且链上协议数据组和审计记录是最新的，否则激活将失败为关闭状态。仅启用配置标志是不够的。

## 金融交易结算工作流程 {#settlement-workflow}

客户端在本地构建证明和加密胶囊。秘密见证必须保留在本地钱包或本地工作者中；不要将它们序列化到应用程序日志、Python 对象、HTTP 请求或持久协调记录中。

胶囊和每审计员 DEK-封装的认证数据包括精确状态锚定委员会和 `authority_context_height` 的加密摘要值，以及网络、路由/化身，捆绑包、财务转账部分、策略、关键时期和明文加密承诺值。封装密钥不能移动到不同的名单或历史授权主体上下文中。

对于每个单一协议标准的金融转账部分，协调者随后执行以下顺序：

1. 将临时加密材料上传到所有四个验证器，并获取一份符合协议标准的准确 3-4 可用性证书。
2. 请授权审计员获取其胶囊，并使用下面描述的经过身份验证的 `POST` 请求，对其进行解密，重新计算公共绑定，应用本地策略，并提交审批。在策略轮换之后，胶囊访问仅限于保留：当前继任者可以授权对符合条件的历史记录进行读取，但不能为根据旧策略准备的财务转账部分添加批准。
3. 请求从四个验证者准备投票。每个验证者独立验证并持久地暂存增量，然后进行投票。在每个暂存的响应者上保存单个协议标准的 3-4 准备证书。
4. 在每次金融转账部分都有准备证书后，构建不可变的完整准备屏障。请求并保存单个协议标准的 3-或-4 协议最终证书。如果协调者重新启动，请查询参与节点其本地持久的准备和共识最终化证书，选择单个符合协议标准的法定等效证书，并在继续之前重新分发；切勿从未经认证的本地缓存重建证书。
5. 让技术舱单赞助人签署并提交恰好一个全球集装箱交易。该集装箱交易包含一个 `FinalizeAtomicPrivateSettlementV1` 指令和完整的认证包。协调员和 WSV 进行完整类型擦除的完成指令的预检，包括已注册的指令框架。Torii 和核心一次性容器事务绑定在精确的单一协议标准赞助商签署的事务上强制执行 `max_carrier_bytes`，包括授权主体、元数据、费用意图和签名。Torii 会在其授权主体上下文之前、在可能通过到期达成最终性的最后进入高度处或之后，或超过规定的到期跨度时，拒绝容器交易。
6. 查询公共捆绑状态和协议结果记录，直到全局最终性。在与不可变的全局终端记录对账之前，将本地辅助记录状态视为临时的。

Rust 客户端通过包括 `certify_and_upload_private_settlement_legs_v1`、`prepare_private_settlement_bundle_v1`、`commit_private_settlement_bundle_v1` 和 `submit_private_settlement_bundle_v1` 的方法来公开此流程。可重启安全的协调使用 `recover_or_prepare_private_settlement_bundle_v1` 和 `recover_or_commit_private_settlement_bundle_v1`。委员会和审计员的技术调用需要明确的角色凭证；它们不会重用普通账户的加密签名者。

## 安全地轮换审计策略 {#rotate-an-auditor-policy-safely}

使用隐私治理授权的 `RotatePrivateSettlementPoolPolicyV1` 指令。它必须命名当前治理加密摘要的确切数值，保持相同的路由、协议数据组和资产绑定加密承诺值，将治理修订推进一次，使用严格更新的密钥时期和不同的策略/治理加密摘要，并在包含轮换的区块上激活。协议数据组前沿、根、空值器、输出，重放集和最终的协议结果记录已被保留。不要包含在轮换激活高度触及同一路径/池的协议结果记录；该指令拒绝该边界。

公共协议数据组投影保留了完整的已废弃政策修订沿革。因此，在轮换之前最终确定的协议结果记录在重启后仍然作为历史证据有效。在重放那个完全相同的协议结果记录时，会被确定性地拒绝，而不会发生状态变更。血统不授权未完成的工作：任何跨越激活边界的旧策略包都会在全球状态变化之前被封闭地失败。继任政策可以授权仅在属于具有较晚治理修订和密钥时期的相同政策谱系时读取保留的历史胶囊,并且经过验证的当前签名密钥在历史策略和封装-DEK 名单中映射到相同的稳定审计员身份。胶囊仍然使用历史审计员密钥加密：保留那个用于打开它的确切历史解密密钥，或者在销毁密钥之前完成受管理且经过测试的胶囊重新包装。此保留访问权限不允许已轮换/当前策略在旧的准备策略下添加批准。

## Torii 路由族 {#torii-route-family}

这些路由使用单一协议标准 Norito 请求和响应对象。经过认证和受限的响应使用私有 `no-store` 缓存行为。

|操作|方法与路径|校长|
| ------------------ | -------------------------------------------------------------------------- | --------------------------- |
|上传财务转账部分| `POST /v1/nexus/private-settlements/legs`                                  |单一协议标准账户签名|
|可用性共享| `POST /v1/nexus/private-settlements/legs/availability-shares`              |单一协议标准账户签名|
|准备投票| `POST /v1/nexus/private-settlements/phases/prepare-votes`                  |单一协议标准账户签名|
|最终阶段投票| `POST /v1/nexus/private-settlements/phases/commit-votes`                   |单一协议标准账户签名|
|坚持阶段 QC| `POST /v1/nexus/private-settlements/phases/certificates`                   |单一协议标准账户签名|
|恢复阶段 QCs| `GET /v1/nexus/private-settlements/legs/{payload_digest}/phase-certificates` |技术声明赞助商|
|财务转账部分状态| `GET /v1/nexus/private-settlements/legs/{payload_digest}/status`           |单一协议标准账户签名|
|委员会校样| `GET /v1/nexus/private-settlements/legs/{payload_digest}/committee-proof` |精确名单验证器|
|审计胶囊| `POST /v1/nexus/private-settlements/legs/{payload_digest}/audit-capsule`   |受监管的审计员|
|审计员批准| `POST /v1/nexus/private-settlements/legs/{payload_digest}/audit-approvals` |受监管的审计员|
|提交最终/中止| `POST /v1/nexus/private-settlements/bundles`                               |技术声明赞助商|
|捆绑状态| `GET /v1/nexus/private-settlements/bundles/{bundle_id}`                    | 公共 |
|协议结果记录或中止| `GET /v1/nexus/private-settlements/bundles/{bundle_id}/receipt`            | 公共 |

公共状态和协议结果记录 APIs 仅显示已记录的公共字段。特别是，普通财务转账部分状态不会显示审批情况计数或受监管的审计阈值。受限读取故意将丢失、未授权和保留过期的材料合并到同一个不可用响应类别中。

审计胶囊操作是只读的、绑定身份的 `POST`，而不是 `GET`。其签名的 Norito JSON 请求体正好是 `{"audit_policy": <PrivateSettlementAuditPolicyV1>}`：完整的当前受管政策是授权的证据，而不是客户端提供的授权主体。节点将胶囊的历史`audit_policy`绑定到技术清单`authority_context_height`生效的治理修订，将请求的当前或继任策略绑定到节点权威读高度生效的修订，并通过两个策略共享的稳定审计员身份映射经过认证的签名密钥。经过认证的响应回显历史记录 `audit_policy` 并用于访问的确切策略为 `access_audit_policy`，响应者证明绑定了两者。客户端必须要求 `access_audit_policy` 等于请求中发送的策略。

提交路径仅接受一个由直接赞助者签署的最终化或中止指令。其 `202` 响应仅包含捆绑 ID、观察到的准入高度和容器交易的加密哈希；它不声明排队的中止已是最终状态。 SDKs 要求两个标识符都为单协议标准校验的 Norito `Hash` JSON 字面量，并且高度必须是精确的无符号 64 位整数；缺失、附加、输入错误、非单一协议标准、校验和无效、负数、负零、小数或溢出字段会导致关闭。使用捆绑状态或协议结果记录作为权威终端状态。状态代码也是完全相同的：此容器事务-接纳路径需要 `202`，而每个其他私人结算 V1 成功响应则需要 `200`。客户端将替代的成功 `2xx` 代码视为合同偏离，而不会通过客户端错误回显意外的响应主体。它们仅暴露服务器拒绝代码当它与 `[A-Za-z0-9_.:-]{1,128}` 匹配时，并丢弃响应解析器/验证原因，从而防止正文内容或攻击者选择的 JSON 字段名称通过原因感知日志重新出现。

## 失败与恢复 {#failure-and-recovery}

缺失或过期的审计员批准、不足三票的验证者投票、错误的根或时期、重复的作废者、替代的证明或胶囊、非规范的财务部分订单转移、过期捆绑包和不匹配的报销条款在全局变异之前都会失败。共识最终化证书永远不会改变私有状态。

验证者在确认辅助记录、分阶段增量和阶段证书之前会先进行 fsync。重启时，它们从单个协议标准的持久记录重建预留，然后对不可变的全局协议结果记录、中止标记或过期进行调和。即使没有需要调和的终端候选项，受监督的调解器也会在同步观察到的权威高度上运行终端保留修剪。并且它在修剪错误时会关闭。只有权威的全局终端记录才能释放预先锁定的锁。精确的最终协议结果记录的重放和冲突重放都会被确定性地拒绝，而不会改变状态。

保留身份包括完整的路由。协议数据组头使用`(route, pool_id, epoch, root)`，消除器使用`(route, pool_id, nullifier)`，输出使用`(route, pool_id, commitment)`。另一条路由上的相等不透明值是独立的;精确路径碰撞在重启过程中保持锁定。

操作警报应仅使用不透明的捆绑包、路由、阶段、加密摘要值、高度和原因类别字段。切勿在日志、事件、指标标签或追踪跨度中放置解密的胶囊、账户或资产标识符、金额、备注、查看数据、证明见证或解析器有效载荷。

## 真正价值之前的资格 {#qualification-before-real-value}

对于您打算部署的确切构建和配置，请存档涵盖以下内容的证据：

- 对抗性证明、胶囊、策略、密钥轮换、报销和重放案例
- 针对2、3、4、8和16个数据空间的真实四验证者流程，包括验证者和协调者重启、经过身份验证的5%、10%和20%的消息丢失、阶段分区、恢复以及持久性边界崩溃
- 在 Torii、P2P 块、Kura、时点数据视图、查询、事件、日志和遥测上的金丝雀和差分泄漏分析

发布原始和清理后的证据、威胁模型、协议论证、局限性、源码修订ID、硬件描述及审计报告于一个不可变的 DOI 支持的工件。仅靠存储库测试并不能将该功能转变为生产级的 CBDC 金融交易结算系统。

从最终清理的 Iroha 结账处，生成发布源库存并封入该结账外的预先存在的包根目录中：

```sh
python3 scripts/private_settlement_source_evidence.py \
  --repository-root . \
  --bundle-root /absolute/path/to/release-bundle
```

在已暂存、未暂存、未跟踪或未合并的文件以及捕获期间的任何源代码变更上，生产者都会失败。它保留原始源代码修订对象、单一协议标准的 Git 树清单、精确的二进制路径列表、确定性的源代码密封，以及 `Cargo.lock`；在最终发布的技术清单中包含其 JSON 结果的每个制品声明。它不放弃最终的 DOI 包验证器或任何外部发布门控。

源封印是便携且故障时关闭的：生产者和最终验证者解析整个存档的符号链接图，因此一个看似在根目录下但通过另一个链接、循环、`.git` 遍历或 Windows 风格目标逃逸的链接，会在创建链接之前被拒绝。结构化的源和网关报告仅从边界稳定的文件中解析，这些文件的加密摘要值和长度必须与发布技术清单匹配，并且每种源负载类型必须恰好出现一次。

每一个原始故障运行和延迟样本都必须绑定完整的发布源代码版本、一个结构化固定硬件描述的 SHA-256，以及其精确参与者数量配置的 SHA-256。归档一个单一的协议标准配置技术清单，涵盖 N=2、3、4、8、16；每个条目必须引用保留的配置字节，并在每个数据空间中准确声明四个验证器，一个 3-of-4 法定人数，以及强制签名 RS16 DA/RBC。发布验证器会拒绝在不同的构建、硬件配置或网络配置上生成的摘要。每个单独的损失、阶段切割和持久性崩溃行还必须在 SHA-256 范围内命名全球不可重复使用的精确 JSONL 记录引用。经过认证的控制器和原子性捕获工件。发布验证器解析这些加密摘要，并要求这些行与运行身份、试验索引和参数、控制器确认或恢复结果、连续检查计数相匹配，以及零部分可见性和可花费性观察。后期发布的 p95/p99 对比也会拒绝硬件、配置或测量要求与候选系统不同的签名基线。最终验证器从存档的原始样本重新生成所有报告的百分位数、MADs 和确定性置信区间，而不是依赖独立的基准摘要。它同样会重新加载金丝雀技术清单，并独立重新扫描每个存档的隐私表面，因此在重新绑定文件加密摘要后，报告无法抑制植入的秘密命中。每一个仅限秘密的运行都必须保留其仅限所有者的未过滤回环抓包（pcap）、原始 tcpdump 标准错误输出和零丢包统计、单协议标准端口技术清单、打包的受限源代码归档，以及所有对等方的原子性观察。最终验证器重新运行基于端口的分组拆分、源投影以及从那些归档字节中进行的基线到终端的原子性检查，而不是信任已发布的摘要。

档案还必须包括单一协议标准的成对流量计数和差分对技术清单，绑定每个必需隐私表面的准确左右文件路径、类型、字节长度和 SHA-256 加密摘要。其声明的根目录必须恰好包含配对的归档清单。验证器要求普通表面具有相等的整文件大小和 JSON 公共形状。承载熵的原始回环捕获和打包的受限源档案是明确的大小例外；它改为比较数据包链路类型和每个数据包的长度、受限源身份以及固定形状的行长度。每个 Torii 请求/响应、公共/受限 P2P 数据包、块、查询、事件、日志和遥测流量计数也必须匹配。数据包形状变化、同尺寸结构泄漏、虚假来源声明,或者未配对的文件无法通过重写泄露报告及其加密哈希来隐藏。
