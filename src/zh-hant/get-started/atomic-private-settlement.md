# 運行原子私有跨數據空間金融交易結算 {#run-atomic-private-cross-dataspace-settlement}

`AtomicPrivateSettlementV1` 在每個 2 至 255 個 SORA Nexus 資料空間中協調一個機密財務轉移部分，並在一個全局狀態中完成每個財務轉移部分交易。被拒絕、過期或中止的包不適用任何財務轉移部分。透明原生 AMX DvP/PvP 保持為獨立的協議路徑。

::: warning 發行狀態
此功能受限制，預設為禁用，尚未達到生產資格。在功能正式發布之前，請勿啟用其用於真實的 CBDC 值。隱私、錯誤、性能、可重現構建、獨立加密審查以及產物發布關卡均已通過該版本的檢驗。
:::

## 協議隱藏的內容 {#what-the-protocol-hides}

每個金融轉帳部分使用固定的兩輸入三輸出私密憑證。委員會驗證者會驗證該憑證和不透明的狀態轉換；他們不會接收到明文的參與方、資產、金額、備註或交易結果。授權的本地審計員解密已填充的審計膠囊，檢查其內容，並簽署目的分離的批准。預設政策接受受管理審計員組的一份批准。

公共容器交易和協議結果記錄故意揭示：

- 網路和套件識別碼
- 參與者資料空間路徑及參與者數量
- 時間和到期高度
- 穩定的不透明協議數據組標識符、根、消除器、密碼學承諾值和固定密文槽
- 委員會授權原則及精確的 3-of-4 可用性、準備及協議最終證書
- 贊助商、公共網路費用及終端狀態

這是內容保密，而不是流量匿名。時間、參與者數量、數據空間身份以及穩定池活動仍然是公開的。一個只承載一個 CBDC 的數據空間，即使沒有發布字面上的資產標識，也可能使資產從路徑中被推斷出來。

每個固定的加密輸出都會發布一個 `recipient` 識別碼，此識別碼來自其授權的一次性輸出查看金鑰。在一個財務轉移部分中的三個識別碼必須互不相同；完整的準備屏障和協議結果記錄會將該檢查擴展到所有財務轉移部分。在投票準備之前，每個委員會驗證者也會拒絕已存在於已最終確定的 WSV 中的標識符。全局最終確定在已最終確定的捆綁歷史中執行相同的規則，並具有確定性的接收者索引。該索引不包含在時間點數據視圖有效載荷中，並在還原期間從單一協議標準加密輸出重建，因此已保存的重複項將封閉失敗。這是一個一次性標識符和重放邊界，而不是保證惡意發送者或網路觀察者在發布前無法關聯流量。

## 部署需求 {#deployment-requirements}

在啟動之前，操作員需要具備以下所有條件：

1. 每個參與的數據空間正好四個驗證者，具有不同的 BLS 共識密鑰和持有證明
2. 強制 Sumeragi DA/RBC 為每個高度啟用
3. 每個數據空間中的一個受管控的機密財務交易結算協議數據組和初始根
4. 一個活躍的 V1 私人備忘錄功能以及單獨的財務交易結算證明檔案
5. 至少一個受管理的本地 `PrivateSettlementAuditPolicyV1`，包括不同的審計員簽名和混合加密密鑰、密鑰時期、高度有效性以及批准閾值
6. 足夠的私人輔助記錄存儲以符合配置的保留期限
7. 可以提交最終公共容器交易的中立贊助商帳戶

審計員也可以操作驗證器，但必須使用獨立的共識鍵、審計員簽名鍵和審計員加密鍵。請將退役的解密鍵保留至法規規定的保存期限，或在退役之前管理並測試封裝重包裝。

四驗證者授權原則是由狀態錨定的，而非由客戶端提供。在技術清單的 `authority_context_height`，每個驗證者都從共識狀態解析精確的排序通道/數據空間名單和活動執行通道實例，並要求解析出的高度匹配，並驗證四個 BLS 金鑰和持有證明。上傳、準備以及最終協議結果記錄的承認都使用相同的歷史授權原則。

預備障礙、最終協議最終化捆綁以及協議結果記錄共享一個緊湊的兩級授權主目錄。其 `rosters` 包含路由自由的驗證者身份以及對齊的 BLS 所有權證明，在單一協議標準的首次使用順序中去重。`leg_roster_indices[i]` 選擇技術清單財務轉移部分的名冊 `i`。階段證書的 `authority_catalog_index` 仍然是邏輯清單-等級序號，而不是名冊索引。在權威摘要或 QC 驗證之前，驗證者將該技術性清單金融轉移部分的精確路徑和活躍執行通道化身與選定名冊結合起來，以重建路徑綁定的 `PrivateSettlementCommitteeAuthorityV1`。

## 配置入場 {#configure-admission}

所有生產行為都來自節點配置。環境變數無法啟動此路徑。預設隨附的是 `enabled = false`；保持此功能禁用不需要任何結算特定的配置。

在治理部門已登記所需的功能並選擇了具有充分通知的激活高度後，請一致地配置每個相關節點：

```toml
[nexus.atomic_private_settlement]
enabled = true
activation_height = 500000
minimum_activation_notice_blocks = 7200
proof_profile_version = 1
max_participants = 255
max_expiry_blocks = 7200
audit_timeout_blocks = 1200
prepare_timeout_blocks = 1200
commit_timeout_blocks = 1200
capsule_padding_classes_bytes = [4096, 16384, 65536, 262144]
max_proof_bytes = 8388608
max_capsule_bytes = 1048576
max_carrier_bytes = 4194304
sidecar_retention_blocks = 1000000
sidecar_max_records = 256
sidecar_max_total_bytes = 3221225472
default_min_auditor_approvals = 1
permitted_policy_versions = [1]
```

該示例使用的是出廠的 V1 限制，而不是性能建議。對儲存、證明、膠囊、容器交易和延遲數據容器進行測量在選擇操作範圍之前，先考慮預期的硬體。三相逾時必須適合 `max_expiry_blocks`，且輔助記錄的保留時間必須至少與該到期窗口相同。

`max_capsule_bytes` 限制整個 `PrivateSettlementAuditCapsuleV1` 的單一協議標準 Norito 編碼：AAD、加密隨機數值、密文、向量框架、審計員身份，以及每個封裝的 DEK 行。這不是僅針對密文的限制。每個配置的填充類別必須至少適合 `default_min_auditor_approvals` 名審核員的保守整膠囊數據容器。Torii 也拒絕了一個新的承認的政策，其 `min_approvals` 低於規定的下限，並且拒絕任何完整單一協議標準編碼過大的實際膠囊。

`max_carrier_bytes` 限制完整的單一協議標準贊助者簽署交易，而不僅僅是認證捆綁。此計數包括已註冊的指令框架、交易授權原則和元數據、費用意圖以及簽名。普通網路交易限制仍然作為獨立的上限適用。

除非被管理的能力已啟用，其狀態和啟用高度符合通知期間，編譯的證明檔案與 V1 匹配，且鏈上協議數據組和審計記錄是最新的，否則啟動將失效。僅啟用配置標誌是不夠的。

## 金融交易結算工作流程 {#settlement-workflow}

客戶端在本地構建證明和加密封裝。秘密見證必須保留在原生錢包或原生工作者中；不要將它們序列化到應用程序日誌、Python 對象、HTTP 請求或持久協調記錄中。

膠囊和每位審計員 DEK-包裝的認證數據包含精確狀態錨定委員會和 `authority_context_height` 的加密摘要值，以及網路、路由/化身，捆綁包、財務轉帳部分、政策、關鍵時期以及明文密碼承諾值。封裝密鑰不能移動到不同的名冊或歷史授權主體上下文中。

對於每一個單一協議標準的金融轉移部分，協調者接著執行以下序列：

1. 將臨時加密資料上傳到所有四個驗證者，並獲得單一協議標準的準確 3-出-4 可用性證書。
2. 請授權的審計員使用下文描述的經驗證 `POST` 請求取回其膠囊，解密它，重新計算公眾綁定，應用本地策略，並提交批准。政策輪換後的膠囊訪問僅限於保留：當前的繼任者可以授權有資格的歷史讀取，但不能向依舊政策準備的財務轉移部分添加批准。
3. 請求四個驗證者準備投票。每個驗證者獨立驗證並持久地暫存差異後再投票。在每個已暫存的回應者上持久化單一的符合協議標準的 3-of-4 準備證書。
4. 在每次財務轉帳部分都有一個準備證書後，建立不可變的完整準備屏障。請求並保存單一協議標準的3-對-4協議完成證書。如果協調者重新啟動，請查詢參與節點其本地持久的 Prepare 和共識最終證書，選擇一個單一的協議標準的法定等效證書，並在繼續之前重新分發；切勿從未經身份驗證的本地緩存重建證書。
5. 請技術清單贊助人簽署並提交正好一個全球集裝箱交易。該集裝箱交易包含一個 `FinalizeAtomicPrivateSettlementV1` 指令以及完整且經認證的套件。協調員與 WSV 預檢完整的類型抹除最終化指令，包括已註冊的指令構架。Torii 與核心一次性容器交易綁定強制 `max_carrier_bytes` 遵循精確的單一協議標準贊助人簽署交易，包括授權主體、元資料、費用意圖和簽名。 Torii 在其授權主體上下文之前，或在可能通過到期達到最終性的最後進入高度時或之後，或超過管理的到期跨度時，拒絕容器交易。
6. 查詢公共捆綁狀態和協議結果記錄，直到全球最終性。將本地輔助記錄狀態視為臨時，直到其與不可變的全球終端記錄對帳。

Rust 客戶端通過包括 `certify_and_upload_private_settlement_legs_v1`、`prepare_private_settlement_bundle_v1`、`commit_private_settlement_bundle_v1` 和 `submit_private_settlement_bundle_v1` 的方法來暴露這個流程。可重啟安全的協調使用 `recover_or_prepare_private_settlement_bundle_v1` 和 `recover_or_commit_private_settlement_bundle_v1`。委員會和審計員的技術調用需要明確的角色憑證；它們不會重用普通帳戶的加密簽名者。

## 安全地輪換審計員政策 {#rotate-an-auditor-policy-safely}

使用隱私治理授權的 `RotatePrivateSettlementPoolPolicyV1` 指令。它必須命名當前治理的精確加密摘要值，保持相同路徑、協議數據組和資產綁定加密承諾值，使治理修訂前進一個版本，使用嚴格更新的金鑰時代及不同的政策/治理加密摘要，並在包含輪換的區塊啟動。協定資料群組前沿、根、nullifier、輸出，重播集和最終的協議結果記錄會被保留。不要包含在輪換啟動高度接觸同一路徑/池的協議結果記錄；該指令會拒絕該邊界。

公共協議數據組投影保留完整的已被取代的政策修訂沿革。因此，在輪換之前完成的協議結果記錄在重啟後仍然有效，作為歷史證據。在重放那個精確的協議結果記錄時，會被決定性地拒絕，且不會改變狀態。血統不允許未完成的工作：任何跨越啟動邊界的舊政策捆綁在全局狀態更改之前都會封閉失敗。繼任政策可以授權僅在屬於與後續治理修訂和關鍵時期相同政策血統時才可讀取的保留歷史封裝，且已驗證的當前簽署金鑰對應於歷史政策和封裝-DEK 名冊中的相同穩定審計員身份。該膠囊保持加密狀態，使用歷史審計員金鑰：保留那個精確的歷史解密金鑰以打開它，或在銷毀金鑰之前完成受控和測試過的膠囊重新包裝。這個保留訪問權限不允許已輪換/當前政策在舊的已準備政策下添加批准。

## Torii 路線系列 {#torii-route-family}

這些路由使用單一協議標準 Norito 請求和回應對象。已驗證和受限的回應使用私人 `no-store` 快取行為。

|操作|方法與路徑|校長|
| ------------------ | -------------------------------------------------------------------------- | --------------------------- |
|上傳財務轉帳部分| `POST /v1/nexus/private-settlements/legs`                                  |單一協議標準帳戶簽名|
|可用性分享| `POST /v1/nexus/private-settlements/legs/availability-shares`              |單一協議標準帳戶簽名|
|準備投票| `POST /v1/nexus/private-settlements/phases/prepare-votes`                  |單一協議標準帳戶簽名|
|最終階段投票| `POST /v1/nexus/private-settlements/phases/commit-votes`                   |單一協議標準帳戶簽名|
|持續階段 QC| `POST /v1/nexus/private-settlements/phases/certificates`                   |單一協議標準帳戶簽名|
|恢復階段 QCs| `GET /v1/nexus/private-settlements/legs/{payload_digest}/phase-certificates` |技術公告贊助商|
|財務轉帳部分狀態| `GET /v1/nexus/private-settlements/legs/{payload_digest}/status`           |單一協議標準帳戶簽名|
|委員會校樣| `GET /v1/nexus/private-settlements/legs/{payload_digest}/committee-proof`  |精確名單驗證器|
|審計膠囊| `POST /v1/nexus/private-settlements/legs/{payload_digest}/audit-capsule`   |受管轄審計員|
|審計員批准| `POST /v1/nexus/private-settlements/legs/{payload_digest}/audit-approvals` |受管轄審計員|
|提交最終/中止| `POST /v1/nexus/private-settlements/bundles`                               |技術公告贊助商|
|捆綁狀態      | `GET /v1/nexus/private-settlements/bundles/{bundle_id}`                    |公共|
|協議結果記錄或中止| `GET /v1/nexus/private-settlements/bundles/{bundle_id}/receipt`            |公共的|

公共狀態和協議結果記錄 APIs 僅公開記錄的公共欄位。特別是，普通財務轉帳部分的狀態不會顯示批准情況計數或被管理的審計閾值。受限讀取故意將缺失、未授權和超過保留期限的資料合併到同一個不可用的回應類別中。

審計膠囊操作是一個唯讀、與身份綁定的 `POST`，而不是 `GET`。其簽名的 Norito JSON 請求主體正是 `{"audit_policy": <PrivateSettlementAuditPolicyV1>}`：完整的當前受管政策是授權的證據，而非客戶端提供的授權主體。該節點將膠囊的歷史 `audit_policy` 綁定到技術清單的 `authority_context_height` 生效的治理修訂，將請求的當前或後續政策綁定到節點權威讀取高度下生效的修訂，並通過雙方政策共享的穩定審計員身份映射經認證的簽名密鑰。經認證的回應回顯歷史 `audit_policy` 並用於訪問的精確策略為 `access_audit_policy`，且響應者聲明綁定二者。客戶端必須要求 `access_audit_policy` 等於請求中發送的策略。

提交路由僅接受一個直接由贊助者簽署的最終化或中止指令。其 `202` 回應僅包含捆綁 ID、觀察到的准入高度及容器交易的加密雜湊；它不表示已排隊的中止操作已經最終化。該 SDKs 要求兩個標識符都必須是單一協議標準的校驗和 Norito `Hash` JSON 字面值，且高度必須是精確的無符號 64 位整數；缺失、額外、輸入錯誤、非單一協議標準、校驗和無效、負數、負零、分數值或溢出的欄位將失效封閉。使用捆綁狀態或協議結果記錄來取得權威的終端狀態。狀態代碼也是完全相同的：此容器交易入場路徑需要 `202`，而其他所有私人結算 V1 成功回應都需要 `200`。客戶拒絕將其他成功的 `2xx` 代碼視為合約偏移，而不會通過客戶端錯誤回傳意外的響應主體。他們僅暴露伺服器拒絕代碼當它匹配 `[A-Za-z0-9_.:-]{1,128}` 並丟棄響應解析器/驗證的原因時，可防止正文內容或攻擊者選擇的 JSON 欄位名稱通過原因感知的日誌重新出現。

## 失敗與恢復 {#failure-and-recovery}

缺失或過期的審計員批准、少於三個驗證者投票、錯誤的根或紀元、重複的消耗標識、替換的證明或膠囊、非標準金融部分訂單轉移、過期的捆綁包以及不匹配的報銷條款在全局變異之前都會失敗。共識最終證書從不變更私有狀態。

驗證者在確認輔助記錄、分段增量和階段證書之前，會先執行 fsync。在重啟時，它們會從單一協議標準的持久記錄重建保留，然後對不可變的全局協議結果記錄、中止標記或到期進行對賬。即使沒有終端候選需要調節，受監督的調節器也會在同步觀察到的權威高度執行終端保留修剪，並且在修剪錯誤時會關閉。只有權威的全局終端記錄才能釋放已暫存的鎖。精確的最終協議結果記錄回放和衝突回放都會在不改變狀態的情況下被確定性地拒絕。

保留身份包括完整路由。協議數據組標頭使用 `(route, pool_id, epoch, root)`，消除器使用 `(route, pool_id, nullifier)`，輸出使用 `(route, pool_id, commitment)`。另一條路線上的相等不透明值是獨立的；精確路線碰撞在重啟後仍然保持鎖定。

操作警報應僅使用不透明的捆綁包、路由、階段、加密摘要值、高度和原因類別欄位。切勿在日誌、事件、度量標籤或追蹤跨度中放置已解密的封裝、帳戶或資產標識符、金額、備註、查看數據、證明證人或解析器有效載荷。

## 在實際價值之前的資格 {#qualification-before-real-value}

針對您打算部署的精確建置和配置，存檔涵蓋以下內容的證據：

- 對抗性證明、膠囊、政策、密鑰輪換、報銷和重播情況
- 針對 2、3、4、8 和 16 個資料空間的真實四驗證者過程，包括驗證者和協調者的重啟、驗證的 5%、10% 和 20% 訊息遺失、階段分區、恢復以及持久性邊界崩潰
- 金絲雀與差異滲漏分析，跨越 Torii、P2P 區塊、Kura、時間點資料視圖、查詢、事件、日誌與遙測
- 每位實際網路參與者至少五次預熱和三十個測量的數據包，包含 p50、p95、p99、信賴區間、資源、流量、證明與協議結果記錄大小，以及透明的 AMX 作為控制
- 嚴格的工作區測試、語法檢查和格式檢查、隨機化種子、浸泡測試、可重現的構建、SBOMs，以及已簽署的工件加密哈希
- 兩個正式層：3/255 腿數對稱性檢查和精確的四驗證者委員會索引 N=2 驗證者聚焦加上完整有界故障、論文主要 N=3 故障、N=4 清潔，以及 N=3 到期/重播配置，每個委員會的故障預算獨立
- 對證明關係、虛擬槽選擇器、資產與膠囊綁定、補償關係、密碼學及跨數據空間狀態機的獨立審查

發布原始和已清理的證據、威脅模型、協議論證、限制、源代碼修訂ID、硬體描述及審核報告於一個不可變的 DOI 支持的工件。僅僅倉庫測試並不能將該功能轉變為生產級的 CBDC 金融交易結算系統。

從最終清理的 Iroha 結帳，生成發行源庫存，並封入該結帳之外的預先存在的捆綁根目錄：

```sh
python3 scripts/private_settlement_source_evidence.py \
  --repository-root . \
  --bundle-root /absolute/path/to/release-bundle
```

製作人在已暫存、未暫存、未追蹤或未合併的檔案，以及捕獲過程中的任何來源變更上都會失敗。它保留原始源代碼修訂物件、單一協議標準的 Git 樹清單、精確的二進位路徑清單、確定性的源碼封印，以及 `Cargo.lock`;在最終發佈技術清單中包含其 JSON 結果的每個工件聲明。它不會放棄最終的 DOI 捆綁驗證器或任何外部發佈門檻。

來源印章是可攜的且故障時會關閉：生產者和最終驗證者會解析整個已存檔的符號連結圖，因此任何看似在根目錄內但透過其他連結逃逸的連結、循環、`.git` 遍歷，或 Windows 風格的目標，在建立連結之前都會被拒絕。結構化的來源和閘道報告僅從有界的穩定文件中解析，這些文件的加密摘要值和長度必須與發布技術清單匹配，且每種來源有效載荷類型必須恰好出現一次。

每個原始故障運行和延遲樣本都必須綁定完整的發布源代碼修訂版本、一個結構化固定硬件描述的 SHA-256，以及其精確參與者數量配置的 SHA-256。存檔單一協議標準配置技術清單，涵蓋 N=2,3,4,8,16；每個條目必須引用保留的配置位元組，並在每個數據空間中精確聲明四個驗證者，3-對-4 法定人數，以及強制簽署 RS16 DA/RBC。釋出驗證器會拒絕在不同的版本、硬體配置或網路配置上產生的摘要。每個單獨的損失、階段切割和持久性崩潰行還必須另外命名在 SHA-256-範圍內全球不可重用的精確 JSONL 記錄參考經過驗證的控制器和原子性捕獲工件。釋出驗證器解析這些加密摘要，並要求行與運行識別、試驗索引和參數、控制器確認或恢復結果、連續檢查計數相匹配，以及零部分可見性和可支出性觀察。稍後發布的 p95/p99 比較也否決了其硬體、配置或測量要求與候選版本不同的簽署基線。最終驗證者會從存檔的原始樣本重新生成所有報告的百分位數、MADs 和確定性信賴區間，而不是依賴獨立的基準總結。它同樣會重新加載金絲雀技術清單，並獨立重新掃描每個已存檔的隱私表面，因此在重新綁定文件加密摘要後，報告無法抑制植入的秘密命中。每個僅限秘密的運行必須保留其僅限擁有者的未過濾迴環抓包（pcap）、原始 tcpdump 標準錯誤輸出和零丟包統計、單一協議標準端口技術清單、封裝的受限來源檔案，以及所有對等節點的一致性觀察。最終驗證器重新運行與埠綁定的封包分割、來源投影以及從那些存檔的位元組進行基線到終端原子性檢查，而不是信任已公佈的摘要。

檔案庫還必須包括單一協議標準的配對流量計數和差分配對技術清單，綁定每個所需隱私表面的精確左右檔案路徑、類型、位元組長度以及 SHA-256 加密摘要。其聲明的根必須精確包含成對的檔案庫清單。驗證器要求普通表面的整個檔案大小相等且具有 JSON 公共形狀。承載熵的原始迴送捕獲和打包的受限來源檔案是明確的大小例外；它反而比較封包連接類型和每個封包的長度、受限來源的身份，以及固定形狀的行長。每一個 Torii 請求/回應、公有/受限 P2P 封包、區塊、查詢、事件、日誌和遙測流量計數也必須匹配。封包形狀變化、同尺寸結構洩漏、虛假來源聲明,或未配對的檔案無法透過重寫洩露報告及其加密雜湊來隱藏。
