# Atomic Private Cross-Dataspace ဘဏ္ဍာရေး ငွေကြေးငွေပေးချေမှု Settlement ကို Run {#run-atomic-private-cross-dataspace-settlement}

`AtomicPrivateSettlementV1` သည် 2 မှ 255 အထိရှိသော SORA Nexus ဒေတာဘေ့စ်များတွင် လျှို့ဝှက် ငွေကြေးလွှဲပြောင်းမှု အစိတ်အပိုင်းတစ်ခုစီကို ညှိနှိုင်းပြီး ကမ္ဘာ့နိုင်ငံတစ်နိုင်ငံတွင် ငွေကြေး လွှဲပြောင်းမှုအစိတ်အပိုင်းတိုင်းကို အဆုံးသတ်သည်။ ငွေကြေးလွှဲပြောင်းမှုအစိတ်အပိုင်းတစ်ခုမှ ပယ်ချခံရသော၊ သက်တမ်းကုန်ဆုံးသွားသည့် (သို့) ရပ်ဆိုင်းထားသော ဘန်ဒယ်တစ်ခုမှာ အသုံးမပြုပါ။ Transparent Native AMX DvP/PvP သည် သီးခြားပရိုတိုကောလမ်းကြောင်းတစ်ခုဖြစ်နေဆဲဖြစ်သည်။

::: warning လွတ်မြောက်မှုအခြေအနေ
ဒီ feature ကို ထိန်းချုပ်ထားပြီး အလိုအလျောက် disabled လုပ်ထားပြီး ထုတ်လုပ်မှု အရည်အသွေးမရှိသေးပါ။ ထုတ်ဝေထားတဲ့ functional မတိုင်မီအထိ အမှန်တကယ် CBDC တန်ဖိုး အတွက် activate မလုပ်ပါနဲ့။ privacy, fault, performance, reproducible-build, independent-cryptographic-review နဲ့ artefact-publication gates အားလုံးဟာ တိကျတဲ့ ထုတ်ပြန်မှုအတွက် ကျော်လွန်သွားပါပြီ။
:::

## ဒီပရိုတိုကောက ဘာကို ဖုံးကွယ်ထားလဲ။ {#what-the-protocol-hides}

ဘဏ္ဍာရေးလွှဲပြောင်းမှု အစိတ်အပိုင်းတစ်ခုစီမှာ တည်ငြိမ်သော နှစ်ဝင်၊ သုံးထွက် Private-note သက်သေကို အသုံးပြုသည်။ ကော်မတီအတည်ပြုသူများက သက်သေခံချက်နှင့် မရှင်းလင်းတဲ့အခြေအနေကူးပြောင်းမှုကို စစ်ဆေးကြသည်; ၎င်းတို့ဟာ ရှင်းလင်းသော စာသားပါတီများ၊ အရင်းအမြစ်၊ ပမာဏ၊ မှတ်စု သို့မဟုတ် စီးပွားရေး ရလဒ်များကို မရရှိပါ။ ခွင့်ပြုထားတဲ့ ဒေသတွင်း စာရင်းစစ်သူက ပိတ်ထားတဲ့ စာရင်းစစ်ဆေးမှုပုဒ်မကို ဖေါ်ထုတ်ပြီး ဒီအထဲမှာ ပါဝင်တာကို စစ်ဆေးပြီး ရည်ရွယ်ချက် သီးခြား အတည်ပြုချက်ကို လက်မှတ်ထိုးပါတယ်။ ပုံမှန် မူဝါဒအရ အုပ်ချုပ်တဲ့ စာရင်းစစ်မှူးစုထံမှ အတည်ပြုချက် တစ်ခုကို လက်ခံတယ်။

အများပြည်သူ ကွန်တိန်နာ ကုန်သွယ်မှုနှင့် ပရိုတိုကော ရလဒ် မှတ်တမ်းမှာ ရည်ရွယ်ချက်ရှိပြီး ဖော်ပြထားပါတယ်-

- ကွန်ရက်နှင့် အစုအဝေး မှတ်သားချက်များ
- ပါဝင်သူ ဒေတာဇုန်လမ်းကြောင်းများနှင့် ပါဝင်သူအရေအတွက်
- အချိန်ကာလနှင့် သက်တမ်းကုန်ဆုံးမှု အမြင့်
- Stable opaque protocol data group identifier များ၊ root များ၊ nullifiers များ၊ cryptographic commitment တန်ဖိုးများနှင့် fixed ciphertext slots များ
- ကော်မတီ ခွင့်ပြုချက် မူဝါဒများနှင့် တိကျသော 3-of-4 ရရှိနိုင်မှု, ပြင်ဆင်ခြင်း, နှင့်ပရိုတိုကောအပြီးသတ်သတ်မှတ်ချက်များ
- ပံ့ပိုးသူ၊ အများသုံးကွန်ရက် အခကြေးနဲ့ terminal status

ဤသည်မှာ ယာဉ်ကြောစီးဆင်းမှု အမည်မဲ့ခြင်းမဟုတ်ဘဲ အကြောင်းအရာ လျှို့ဝှက်ချက်ဖြစ်သည်။ အချိန်ဆွဲခြင်း၊ ပါဝင်သူအရေအတွက်၊ ဒေတာနေရာအသိအမှတ်ပြုမှု၊ တည်ငြိမ်တဲ့စုပေါင်းလုပ်ဆောင်မှုက အများပြည်သူအဖြစ် ကျန်ရှိနေသည်။ တစ်ခုတည်းသော CBDC ကို တည်းခိုထားသည့် ဒေတာဇုန်တစ်ခုသည် စာလုံးဝင်လက်ရှိ asset ID မထုတ်ဝေသော်လည်းလည်း လမ်းကြောင်းမှ asset ကိုဖယ်ရှားနိုင်စေနိုင်ပါတယ်။

ပုံသေကုဒ်ဝှက်ထားသည့် အထွက်တစ်ခုစီသည် ခွင့်ပြုထားသော တစ်ကြိမ်သုံး အထွက်ကြည့်ရှုရေးသော့မှ ဆင်းသက်သည့် `recipient` အမှတ်အသားကို ထုတ်ပြန်သည်။ ငွေကြေးလွှဲပြောင်းမှုအပိုင်းတစ်ခုအတွင်းရှိ အမှတ်အသားသုံးခုသည် မတူညီရမည်ဖြစ်ပြီး၊ ပြည့်စုံသော Prepare အတားအဆီးနှင့် ရလဒ်မှတ်တမ်းက ထိုစစ်ဆေးမှုကို အပိုင်းအားလုံးအနှံ့ တိုးချဲ့သည်။ Prepare အတွက် မဲမပေးမီ ကော်မတီအတည်ပြုသူတစ်ဦးစီသည် နောက်ဆုံးအတည်ပြုပြီးသော WSV ထဲတွင် ရှိပြီးသား အမှတ်အသားကိုလည်း ပယ်ချသည်။ ကမ္ဘာလုံးဆိုင်ရာ အပြီးသတ်ခြင်းသည် သတ်မှတ်ချက်တကျ လက်ခံသူအညွှန်းဖြင့် အပြီးသတ်ပြီးသော bundle သမိုင်းတစ်လျှောက် ထိုစည်းမျဉ်းကိုပင် ကျင့်သုံးသည်။ အညွှန်းကို snapshot payload များထဲ မထည့်ဘဲ ပြန်လည်ရယူရာတွင် စံသတ်မှတ်ထားသော ကုဒ်ဝှက်အထွက်များမှ ပြန်လည်တည်ဆောက်သောကြောင့်၊ သိမ်းဆည်းထားသည့် ထပ်တူအမှတ်အသားကို တွေ့ပါက စနစ်သည် အခြေအနေမပြောင်းဘဲ လုံခြုံစွာ ပယ်ချသည်။ ဤသည်မှာ တစ်ကြိမ်သုံးအမှတ်အသားနှင့် ပြန်လည်တင်သွင်းမှုကို တားဆီးသည့် နယ်နိမိတ်ဖြစ်ပြီး၊ မသမာသော ပေးပို့သူ သို့မဟုတ် ကွန်ရက်စောင့်ကြည့်သူက မထုတ်ပြန်မီ လမ်းကြောင်းဆက်နွယ်မှုကို မခန့်မှန်းနိုင်ကြောင်း အာမခံခြင်းမဟုတ်ပါ။

## အသုံးချမှု လိုအပ်ချက်များ {#deployment-requirements}

မဖွင့်ခင် operator တွေဟာ အောက်ပါအချက်တွေအားလုံးကို လိုအပ်ပါတယ်။

1. ပါဝင်တဲ့ ဒေတာနေရာတိုင်းအတွက် အတိအကျ validator လေးခုရှိပြီး ကွဲပြားခြားနားသော BLS သဘောတူညီချက် ခလုတ်များနှင့် ပိုင်ဆိုင်မှု သက်သေခံများရှိသည်။
2. လိုအပ်တဲ့ Sumeragi DA/RBC ကို အမြင့်တိုင်းအတွက် လုပ်နိုင်သည်။
3. စီမံခန့်ခွဲထားသော လျှို့ဝှက်ငွေကြေး ငွေချေးမှု ဖြေရှင်းရေး ပရိုတိုကောဒေါင် အချက်အလက် အုပ်စုနှင့် ဒေတာနေရာတိုင်းတွင် မူလ root ကို
4. Active V1 private note capability နှင့် သီးခြားငွေကြေး ငွေပေးချေမှု ဖြေရှင်းမှု သက်သေပြရေး ပရိုဖိုင်
5. အနည်းဆုံး စည်းကမ်းထားသော ဒေသခံ `PrivateSettlementAuditPolicyV1` တစ်ခု၊ သီးခြားအော်ဒီတာ လက်မှတ်ထိုးခြင်းနှင့် ဟိုက်ဘရစ်ကုဒ်ရေးရာ သော့များ၊ အဓိကခေတ်ကာလ၊ အမြင့် သက်တမ်းနှင့် ခွင့်ပြုချက် တံခါးကိုပါ ၀ င်သည်။
6. ပြင်ဆင်ထားသော ထိန်းသိမ်းမှု ကာလအတွက် လုံလောက်တဲ့ ပုဂ္ဂလိက အထောက်အကူ မှတ်တမ်း သိုလှောင်ခြင်း
7. နောက်ဆုံး အများပြည်သူ ကွန်တိန်နာ ငွေပေးချေမှုကို တင်ပြနိုင်သော ဘက်လိုက် ပံ့ပိုးရေး အကောင့်

Auditor သည် validator ကိုလည်းအသုံးပြုနိုင်သော်လည်း သီးခြားသဘောတူညီချက်၊ Auditor-signing နှင့် Auditor-encryption key များကို အသုံးပြုရမည်။ အသုံးပြုမှုမှ ရပ်စဲထားသော စာဝှက်ဖြည်သော့များ များကို ထိန်းသိမ်းထားခြင်း သို့မဟုတ် decommissioning မပြုလုပ်မီ test capsule ပြန်လည်အုပ်ချုပ်ခြင်း၊ ထိန်းချုပ်ခြင်း။

၄ validator ခွင့်ပြုချက် မူလအချက်အလက်သည် client ကမပေးထားသော state anchored ဖြစ်ပါသည်။ Technical Manifesto `authority_context_height` တွင် validator တစ်ခုချင်းစီကညီညွတ်မှုအခြေအနေမှအတိအကျသတ်မှတ်ထားသော lane / datapace roster နှင့် active execution lane incarnation ကိုဖြေရှင်းသည်။ ဖြေရှင်းသည့်အမြင့်ကိုသင့်တော်စေရန်လိုအပ်သည်။ BLS သော့လေးလုံးနဲ့ ပိုင်ဆိုင်မှု သက်သေခံချက်တွေကို စစ်ဆေးပါတယ်။ Upload, Prepare နဲ့ Final Protocol Result Record admits အားလုံးဟာ သမိုင်းဝင် ခွင့်ပြုချက် မူဝါဒကိုပဲ သုံးတယ်။

Prepare အတားအဆီး၊ နောက်ဆုံး commit bundle နှင့် ရလဒ်မှတ်တမ်းတို့သည် ကျစ်လစ်သည့် နှစ်ဆင့် အာဏာပိုင် catalog တစ်ခုကို မျှဝေသည်။ ၎င်း၏ `rosters` များတွင် လမ်းကြောင်းနှင့်မချည်နှောင်ထားသော အတည်ပြုသူ အမှတ်အသားများနှင့် ကိုက်ညီသည့် BLS ပိုင်ဆိုင်မှုသက်သေများ ပါဝင်ပြီး၊ စံသတ်မှတ်ထားသော ပထမဆုံးအသုံးပြုမှုအစဉ်အတိုင်း ထပ်တူများကို ဖယ်ရှားထားသည်။ `leg_roster_indices[i]` သည် manifest ၏ အပိုင်း `i` အတွက် roster ကို ရွေးသည်။ အဆင့်လက်မှတ်၏ `authority_catalog_index` သည် roster အညွှန်းမဟုတ်ဘဲ manifest အပိုင်း၏ ယုတ္တိအစဉ်နံပါတ်အဖြစ် ဆက်လက်တည်ရှိသည်။ အာဏာပိုင် digest သို့မဟုတ် QC ကို မစစ်ဆေးမီ၊ အတည်ပြုသူများသည် ထို manifest အပိုင်း၏ တိကျသော လမ်းကြောင်းနှင့် လက်ရှိလုပ်ဆောင်ရေး lane incarnation ကို ရွေးထားသော roster နှင့်ပေါင်း၍ လမ်းကြောင်းနှင့်ချည်နှောင်ထားသော `PrivateSettlementCommitteeAuthorityV1` ကို ပြန်လည်တည်ဆောက်သည်။

## Admission ကို Configure လုပ်ပါ။ {#configure-admission}

ထုတ်လုပ်မှုအပြုအမူအားလုံးသည် node ဖွဲ့စည်းချက်မှလာသည်။ ပတ်ဝန်းကျင်ပြောင်းလဲနိုင်သူများက ဤလမ်းကြောင်းကို တက်ကြွမပေးနိုင်ပါ။ ပို့ဆောင်သော default သည် `enabled = false` ဖြစ်သည်၊ feature ကိုပိတ်ထားခြင်းအားဖြင့် settlement-specific ဖွဲ့စည်းမှုတစ်ခုမျှ မလိုပါ။

အုပ်ချုပ်ရေးမှူးက လိုအပ်တဲ့ အရည်အသွေးကို မှတ်တမ်းတင်ပြီးနောက်၊ သင့်တော်သော အသိပေးချက်ဖြင့် တက်ကြွမှု အမြင့်တစ်ခုကို ရွေးချယ်ပြီးနောက်၊ သက်ဆိုင်ရာ node တစ်ခုစီကို စနစ်တကျ ညွှန်ကြားပါ။

```toml
[nexus.atomic_private_settlement]
enabled = true
activation_height = 500000
minimum_activation_notice_blocks = 7200
proof_profile_version = 1
max_participants = 255
max_expiry_blocks = 7200
audit_timeout_blocks = 1200
prepare_timeout_blocks = 1200
commit_timeout_blocks = 1200
capsule_padding_classes_bytes = [4096, 16384, 65536, 262144]
max_proof_bytes = 8388608
max_capsule_bytes = 1048576
max_carrier_bytes = 4194304
sidecar_retention_blocks = 1000000
sidecar_max_records = 256
sidecar_max_total_bytes = 3221225472
default_min_auditor_approvals = 1
permitted_policy_versions = [1]
```

ဥပမာမှာ သယ်ဆောင်ပို့တဲ့ V1 ကန့်သတ်ချက်တွေကို သုံးပြီး စွမ်းဆောင်ရည်ဆိုင်ရာ အကြံပြုချက်မဟုတ်ပါဘူး။ စီမံခန့်ခွဲမှု နယ်နိမိတ်တွေကို ရွေးချယ်ဖို့ ရည်ရွယ်တဲ့ Hardware ကို သုံးဆင့် အချိန်ဖြတ်တောက်တာတွေဟာ `max_expiry_blocks` အတွင်းမှာ တပ်ဆင်ရပြီး အထောက်အကူ မှတ်တမ်း ထိန်းသိမ်းမှုဟာ အနည်းဆုံး သက်တမ်းကုန်ဆုံးတဲ့ ပြတင်းပေါက်ဖြစ်ဖို့လိုပါတယ်။

`max_capsule_bytes` သည် `PrivateSettlementAuditCapsuleV1` တစ်ခုလုံး၏ တစ်ခုတည်းသော ပရိုတိုကော-စံစံညွှန်း Norito ကုဒ်သွင်းခြင်းကို ကန့်သတ်ထားသည် - AAD, cryptographic nonce value, ciphertext, vector framing, စာရင်းစစ်သူ အမှတ်အသားများ နှင့် wrapped-DEK အတန်းတစ်ခုစီ။ ဒါဟာ ciphertext အတွက်သာ ကန့်သတ်ချက်မဟုတ်ပါ။ configured padding class တစ်ခုချင်းစီဟာ အနည်းဆုံး `default_min_auditor_approvals` စာရင်းစစ်သူတွေအတွက် ဂရုစိုက်တဲ့ ကပ်ဆူးတစ်ခုလုံးဆိုင်ရာ ဒေတာအိုးကို လိုက်ဖက်သင့်ပါတယ်။ Torii ကလည်း အသစ်အဆန်းတစ်ခုကို ပယ်ချတယ်။ `min_approvals` သည် ထိန်းချုပ်ထားသောအဆင့်အောက်ရှိ မူဝါဒကိုလက်ခံပြီး တစ်ခုတည်းသော ပရိုတိုကုတ်စံညွှန်းအပြည့်အဝ ကုဒ်သွင်းခြင်းသည် အလွန်ကြီးမားသော သက်ရောက်မှုရှိသည့် အစစ်အကျဉ်းတစ်ခုခုကို ငြင်းပယ်သည်။

`max_carrier_bytes` က ပရိုတိုကော တစ်ခုတည်းသော စံသတ်မှတ်ချက်အရ ထောက်ခံသူလက်မှတ်ထိုးထားတဲ့ ငွေပေးချေမှု အပြည့်အဝကို ကန့်သတ်ထားပြီး အာမခံစာအုပ်တင်မကပဲ မှတ်ပုံတင်ညွှန်ကြားချက်ကိုပါ ၀ င်ပါတယ်။ ဖွဲ့စည်းပုံ၊ ငွေပေးချေမှု ခွင့်ပြုချက် အရင်းအမြစ်နှင့် မက်တာဒေတာများ၊ အခွန် ရည်ရွယ်ချက်နှင့် လက်မှတ်ထိုးခြင်း။ သာမန်ကွန်ရက် ငွေလဲလှယ်မှု ကန့်သတ်ချက်များသည် လွတ်လပ်သော အထက်နိမိတ်တစ်ခုအဖြစ် ဆက်လက်လုပ်ဆောင်သည်။

Activation ကို မပိတ်နိုင်ပါက ထိန်းချုပ်ထားသော အရည်အသွေးသည် တက်ကြွနေမှသာ၊ ၎င်း၏အခြေအနေနှင့် တက်ကြွမှု အမြင့်များသည် ကြေညာချက်ကာလကို ဖြည့်ဆည်းပေးခြင်းမရှိဘဲ၊ စုစည်းထားသည့် သက်သေပြရေး ပရိုဖိုင် V1 နှင့် လက်ရှိ ချိတ်ဆက်ထားတဲ့ ပရိုတိုကောလစ် အချက်အလက်အုပ်စုနှင့် စစ်ဆေးရေး မှတ်တမ်းများ မရှိပါ။ ဖွဲ့စည်းမှု အလံကို သက်ဝင်အောင်လုပ်ခြင်းတစ်ခုတည်းဟာ မလုံလောက်ပါ။

## ငွေရေးကြေးရေးလုပ်ငန်းများ ဖြေရှင်းမှု လုပ်ငန်းစဉ် {#settlement-workflow}

ဖောက်သည်က သက်သေခံချက်များနှင့် ကုဒ်သွင်းထားသော ကပ်ဆူလ်များကို ဒေသတွင်းတွင် တည်ဆောက်သည်။ လျှို့ဝှက်သက်သေများသည် ဒေသခံငွေကြေးစာရင်း (သို့) ဒေသခံအလုပ်သမားအတွင်းမှာနေရမည်ဖြစ်ပြီး လျှောက်လွှာမှတ်တမ်းများ၊ Python အရာဝတ္ထုများ, HTTP တောင်းဆိုချက်များ သို့မဟုတ် ရေရှည်တည်တံ့သည့် ညှိနှိုင်းရေး မှတ်တမ်းများသို့ serialize မလုပ်ရပါ။

Capsule နဲ့ auditor တစ်ခုချင်းအတွက် DEK ပိတ်ထားတဲ့ စစ်ဆေးတဲ့ အချက်အလက်တွေထဲမှာ နိုင်ငံတော်မှာ ခိုင်မာတဲ့ ကော်မတီနဲ့ `authority_context_height` တို့ရဲ့ cryptographic digest value အပါအဝင် network၊ route/incarnation တွေလည်း ပါဝင်ပါတယ်။ ဘက်ဒယ်၊ ငွေကြေးလွှဲပြောင်းမှု အပိုင်း၊ မူဝါဒ၊ သော့ခေတ်နှင့် ရှင်းလင်းသော စာသား cryptographic commitment တန်ဖိုး။ ပိတ်ထားသော သော့ကို အခြားစာရင်းသို့ (သို့) သမိုင်းဝင် ခွင့်ပြုချက် အဓိက အခြေအနေသို့ မပြောင်းနိုင်ပါ။

အစီရင်ခံစာစံညွှန်း ငွေကြေးလွှဲပြောင်းမှု အစိတ်အပိုင်းတစ်ခုစီအတွက် ညှိနှိုင်းရေးမှူးက ဒီအစဉ်ကို လုပ်ဆောင်သည်။

1. ယာယီ ကုဒ်သွင်းထားတဲ့ ပစ္စည်းကို validator လေးခုစလုံးမှာ တင်ပြီး single protocol-standard exact 3-of-4 availability certificate ကို ရယူပါ။
2. အတည်ပြုထားတဲ့ `POST` တောင်းဆိုချက်ကို အောက်မှာဖော်ပြထားပြီး အာမခံခံရတဲ့ စာရင်းစစ်သူတစ်ဦးက သူ့အိတ်ကိုယူလာစေဖို့၊ ကုဒ်ချဖို့၊ အများပြည်သူဆိုင်ရာ ချုပ်နှောင်ချက်တွေကို ပြန်တွက်ဖို့၊ ဒေသတွင်း မူဝါဒကို လိုက်နာဖို့နဲ့ ခွင့်ပြုချက်တင်ပြဖို့။ မူဝါဒလှည့်လည်ပြီးနောက် Capsule ဝင်ရောက်မှုက ထိန်းသိမ်းမှုတစ်ခုတည်းဖြစ်သည်- လက်ရှိဆက်ခံသူက သင့်တော်တဲ့ သမိုင်းဖတ်မှုကို ခွင့်ပြုနိုင်ပေမဲ့ မူဝါဒဟောင်းအရ ပြင်ဆင်ထားသော ဘဏ္ဍာငွေလွှဲပြောင်းမှု အစိတ်အပိုင်းသို့ ခွင့်ပြုချက် မဖြည့်နိုင်ပါ။
3. အတည်ပြုသူ ၄ ဦးမှ မဲများကို ပြင်ဆင်ပါ။ အတည်ပြုသူများတိုင်းက မဲမပေးမီ ဒယ်လ်တာကို သီးသန့်စစ်ဆေးပြီး ရေရှည်တည်တံ့စွာ အဆင့်သတ်မှတ်သည်။ အဆင့်သတ်မှတ်သူတိုင်းအတွက် Single Protocol-Standard 3-of-4 Prepare Certificate ကို ဆက်လက်ထားပါ။
4. ငွေလွှဲပြောင်းမှု အစိတ်အပိုင်းတိုင်းမှာ Prepare Certificate ရှိပြီးနောက် မပြောင်းလဲနိုင်သော Complete Prepare Barrier ကို တည်ဆောက်ပါ။ Single Protocol-Standard 3-of-4 Protocol Finalisation Certificates တွေကို တောင်းဆိုပြီး ဆက်လက်ပြုလုပ်ပါ။ ညှိနှိုင်းရေးမှူးက ပြန်လည်စတင်ပါက ဒေသတွင်း တည်ငြိမ်သော Prepare နှင့် Consensus Finalisation Certificates များအတွက် ပါဝင်သူ node များကို မေးမြန်းပြီး single protocol-standard quorum-equivalent certification ကိုရွေးချယ်ပြီး ဆက်မလုပ်ခင်ပြန်ဖြန့်ချိပါ။ ဘယ်တော့မှ စစ်ဆေးခြင်းမရှိတဲ့ ဒေသတွင်း cache ကနေ Certificate တစ်ခုကို ပြန်လည်တည်ဆောက်ခြင်း။
5. Technical Manifesto Sponsor လက်မှတ်ထိုးပြီး တစ်ကမ္ဘာလုံး container ကုန်သွယ်မှု တစ်ခုကို အတိအကျတင်ပေးပါ။ container transaction မှာ တစ်ခုပါဝင်ပါတယ်။ `FinalizeAtomicPrivateSettlementV1` ညွှန်ကြားချက်နှင့် အတိအကျအပြည့်အဝ Certified Bundle ကို. WSV pre-flight တိုင်းတာမှု မှတ်ပုံတင်ညွှန်ကြားချက် ဖွဲ့စည်းခြင်းအပါအဝင် type-erased အပြီးသတ်ရေး ညွှန်ကြားချက်တစ်ခုလုံး။ Torii နောက်ပြီး ဗဟိုမှာရှိတဲ့ One-Shot Container Transaction ကို ချုပ်ဆိုဖို့ အာဏာပေးတယ်။ `max_carrier_bytes` ပရိုတိုကော တစ်ခုတည်းသော စံနှုန်းဖြင့် ထောက်ခံသူ လက်မှတ်ရေးထိုးထားသည့် ငွေပေးချေမှုအပေါ်၊ ခွင့်ပြုချက် အရင်းအမြစ်၊ မီတာဒေတာ၊ အခွန် ရည်ရွယ်ချက်နဲ့ လက်မှတ်ပါ ၀ င်ပါတယ်။ Torii Container Transaction ကို ခွင့်ပြုချက်ရဲ့ အဓိက အခြေအနေမတိုင်မီမှာ ပယ်ချလိုက်ပါတယ်။ နောက်ဆုံးဝင်ရောက်မှု အမြင့်ချိန်မှာ (သို့) ပြီးဆုံးပြီးနောက်၊ သက်တမ်းကုန်ဆုံးတဲ့အခါမှာ အဆုံးသတ်နိုင်တာ (သို့) သတ်မှတ်ထားတဲ့ သက်တမ်းကုန်လွန်တဲ့ ကာလပါ။
6. ကမ္ဘာလုံးဆိုင်ရာ အပြီးသတ်မှုအထိ အများပြည်သူ ဘန်ဒယ်အခြေအနေနှင့် ပရိုတိုကော ရလဒ်မှတ်တမ်းကို မေးမြန်းပါ။ ဒေသတွင်း အထောက်အပံ့ မှတ်တမ်းအခြေအနေကို မပြောင်းလဲနိုင်တဲ့ ကမ္ဘာလုံးဆိုင်ရာ နောက်ဆုံးမှတ်တမ်းကို ညှိမပေးတဲ့အထိ ယာယီအဖြစ် ဆက်ဆံပါ။

နိုင်ငံတကာ Rust client က ဒီစီးဆင်းမှုကို အပါအဝင်နည်းလမ်းတွေနဲ့ ဖော်ပြတယ်။ `certify_and_upload_private_settlement_legs_v1`, `prepare_private_settlement_bundle_v1`, `commit_private_settlement_bundle_v1`, နှင့် `submit_private_settlement_bundle_v1`. ပြန်လည်စတင်ခြင်း ဘေးကင်းသော ညှိနှိုင်းမှု အသုံးများ `recover_or_prepare_private_settlement_bundle_v1` နှင့် `recover_or_commit_private_settlement_bundle_v1`. ကော်မတီနဲ့ စာရင်းစစ်သူတွေရဲ့ နည်းပညာဆိုင်ရာ တောင်းဆိုချက်တွေဟာ တိကျတဲ့ အခန်းကဏ္ဍကို လိုအပ်ပါတယ်။ မှတ်ပုံတင်အချက်အလက်များ၊ သာမန်စာရင်း cryptographic လက်မှတ်ထိုးသူကို ပြန်လည်အသုံးပြုခြင်း မရှိပါ။

## Auditor Policy ကို လုံခြုံစွာ Rotate လုပ်ပါ။ {#rotate-an-auditor-policy-safely}

Privacy-Governance-authorized `RotatePrivateSettlementPoolPolicyV1` ညွှန်ကြားချက်ကိုအသုံးပြုပါ။ ၎င်းသည်အတိအကျလက်ရှိ အုပ်ချုပ်မှု cryptographic digest တန်ဖိုးကိုဖော်ပြရမည်၊ လမ်းကြောင်းတစ်ခုတည်း၊ ပရိုတိုကုတ်ဒေတာအုပ်စုနှင့် အရင်းအမြစ်ဘောင်သတ်မှတ်သော cryptographic commitment တန်ဖိုးကို ထိန်းထားရမည်။ အုပ်ချုပ်မှု ပြန်လည်သုံးသပ်မှုကို တစ်ဆင့်တိုးမြှင့်ရမည်။ ပရိုတိုကော data group frontier, roots, nullifiers, outputs တွေကို replay set များနှင့် နောက်ဆုံးသတ်မှတ်ထားသော protocol ရလဒ် မှတ်တမ်းများကို သိမ်းဆည်းထားသည်။ rotation ၏ activation အမြင့်တွင်တူညီသော route / pool ကိုထိတွေ့သည့် protocol ရလဒ်မှတ်တမ်းကို မပါ ၀ င်ပါ။ ညွှန်ကြားချက်သည် ထိုနယ်နိမိတ်ကို ငြင်းပယ်သည်။

အများသုံး pool projection သည် အစားထိုးပြီးသော မူဝါဒ revision မျိုးရိုးစဉ်အပြည့်အစုံကို ထိန်းသိမ်းထားသည်။ ထို့ကြောင့် rotation မတိုင်မီ အပြီးသတ်ခဲ့သော ရလဒ်မှတ်တမ်းသည် ပြန်လည်စတင်ပြီးနောက် သမိုင်းအထောက်အထားအဖြစ် ဆက်လက်မှန်ကန်သော်လည်း၊ ထိုရလဒ်မှတ်တမ်းအတိအကျကို ပြန်လည်တင်သွင်းပါက အခြေအနေမပြောင်းဘဲ သတ်မှတ်ချက်တကျ ပယ်ချသည်။ မျိုးရိုးစဉ်သည် မပြီးဆုံးသေးသောလုပ်ငန်းကို ခွင့်မပြုပါ။ activation နယ်နိမိတ်ကို ဖြတ်သည့် မူဝါဒအဟောင်း bundle မည်သည့်အရာမဆို ကမ္ဘာလုံးဆိုင်ရာအခြေအနေ မပြောင်းမီ လုံခြုံစွာ ပယ်ချသည်။ နောက်ဆက်တွဲမူဝါဒသည် နောက်ပိုင်း အုပ်ချုပ်မှု ပြန်လည်ပြင်ဆင်ချက်နှင့် သော့ခေတ် ပါသည့် မူဝါဒမျိုးရိုးစဉ်တူမှသာ သိမ်းထားသော သမိုင်းဝင် capsule ကို ဖတ်ရှုခွင့်ပြုနိုင်ပြီး၊ အတည်ပြုထားသော လက်ရှိလက်မှတ်သော့သည် သမိုင်းဝင်မူဝါဒနှင့် wrapped-DEK roster နှစ်ခုစလုံးရှိ တည်ငြိမ်သော auditor အမှတ်အသားတူသို့ ချိတ်ဆက်ရမည်။ Capsule သည် သမိုင်းဝင် auditor သော့ဖြင့် ကုဒ်ဝှက်ထားဆဲဖြစ်သည်။ ဖွင့်ရန် ထိုသမိုင်းဝင် စာဝှက်ဖြည်သော့အတိအကျကို ထိန်းသိမ်းပါ၊ သို့မဟုတ် သော့မဖျက်မီ အုပ်ချုပ်၍ စမ်းသပ်ထားသော capsule rewrap ကို ပြီးစီးပါ။ ဤထိန်းသိမ်းရေး access သည် rotated/current မူဝါဒအား အဟောင်း prepared မူဝါဒအောက်တွင် အတည်ပြုချက် ထပ်ထည့်ခွင့်မပေးပါ။

အများပြည်သူအခြေအနေနှင့် ပရိုတိုကောလ် ရလဒ်မှတ်တမ်း APIs တွင် မှတ်တမ်းတင်ထားသော အများပြည်သူနယ်မြေများသာ ဖော်ပြထားသည်။ အထူးသဖြင့် သာမန်ငွေလွှဲပြောင်းမှု အစိတ်အပိုင်းအခြေအနေသည် ခွင့်ပြုချက် မပြသပါ။ Restricted read တွေဟာ ပျောက်နေတဲ့၊ ခွင့်မပြုထားတဲ့နဲ့ ထိန်းသိမ်းမှု သက်တမ်းကုန်ဆုံးသွားတဲ့ ပစ္စည်းတွေကို တန်းတူမရနိုင်တဲ့ တုံ့ပြန်မှုတန်းအစားထဲ အလိုအလျောက် ပြုတ်ကျစေပါတယ်။

စာရင်းစစ်ဆေးမှု-ကုလားအုပ်လုပ်ငန်းသည် `GET` မဟုတ်ဘဲ ဖတ်ရန်သာ ချုပ်နှောင်ထားသော `POST` ဖြစ်ပါသည်။ ၎င်း၏ လက်မှတ်ထိုးထားသော Norito JSON request body သည်တိကျစွာ `{"audit_policy": <PrivateSettlementAuditPolicyV1>}` ဖြစ်သည်။ လက်ရှိထိန်းချုပ်သည့် မူဝါဒတစ်ခုလုံးက ခွင့်ပြုချက်အတွက် အထောက်အထားဖြစ်သည်၊ ဖောက်သည်များမှပေးပို့သော ခွင့်ပြုမှု မူဝါဒမဟုတ်ပါ။ node က kapsule ရဲ့ သမိုင်းဆိုင်ရာ `audit_policy` ကို Technical Manifesto ရဲ့ `authority_context_height` မှာ သက်ရောက်တဲ့ အုပ်ချုပ်မှု ပြန်လည်ပြင်ဆင်ချက် နဲ့ ချိတ်ဆက်ပေးပြီး requested current (သို့) successor policy ကို node-authoritative read height မှာ သက်ရောက်နေတဲ့ revision နဲ့ ချည်နှောင်ပေးပါတယ်။ မူဝါဒနှစ်ခုစလုံးက မျှဝေတဲ့ တည်ငြိမ်တဲ့ စာရင်းစစ်သူရဲ့ ကိုယ်ပိုင်လက္ခဏာမှတစ်ဆင့် စစ်ဆေးထားတဲ့ လက်မှတ်ထိုးရေး သော့ကို မြေပုံထုတ်တယ်။ စစ်ဆေးထားတဲ့ တုံ့ပြန်မှုက သမိုင်းဝင် `audit_policy` နှင့် `access_audit_policy` အနေနဲ့ ဝင်ရောက်ခွင့်အတွက် အသုံးပြုခဲ့တဲ့ တိကျတဲ့ မူဝါဒနဲ့ ဖြေကြားသူရဲ့ အတည်ပြုချက် နှစ်ခုစလုံးကို ချိတ်ဆက်ပေးပါတယ်။ ဖောက်သည်တွေဟာ `access_audit_policy` ကို တောင်းဆိုမှုထဲမှာ ပေးပို့ထားတဲ့ မူဝါဒနှင့် ညီမျှဖို့ တောင်းဆိုရပါမယ်။

တင်ပြမှုလမ်းကြောင်းသည် တိုက်ရိုက်ထောက်ခံသူလက်မှတ်ထိုးပြီးဆုံးဖြတ်ခြင်း (သို့) ဖျက်သိမ်းခြင်းညွှန်ကြားချက်တစ်ခုတည်းကို လက်ခံသည်။ `202` တုံ့ပြန်မှုမှာ ဘန်ဒယ် ID၊ မှတ်တမ်းတင်ထားတဲ့ ဝင်ခွင့်အမြင့်နဲ့ အိုးပါ Transaction cryptographic hash ကိုသာ; ၎င်းသည်အလိုအလျောက် abort သည်အပြီးဆုံးဖြစ်ကြောင်းမဆိုပါ။ SDKs Identifier နှစ်ခုစလုံးကို Single Protocol Standard checksum လုပ်ဖို့ လိုအပ်တယ်။ Norito `Hash` JSON literals နဲ့ အမြင့်က လက်မှတ်မထိုးထားတဲ့ 64-bit integer တစ်ခုတည်းဖြစ်ဖို့ပါ။ ပျောက်နေတဲ့၊ ထပ်ဆင့်၊ မှားယွင်းရိုက်တာတွေ၊ တစ်ချိုမဟုတ်တဲ့ ပရိုတိုကော စံနှုန်း။ checksum-invalid၊ negative, negative-zero, fractional သို့မဟုတ် overflowed fields တွေကို ပိတ်ထားခြင်းမရှိပါ။ မူပိုင် terminal state အတွက် bundle status (သို့) protocol result record ကို အသုံးပြုပါ။ အခြေအနေကုဒ်ကလည်း တိကျပါတယ် ဒီ container transaction-admission လမ်းကြောင်းမှာ လိုအပ်တဲ့ `202`, အခြားသော ပုဂ္ဂလိက အခြေချမှုတိုင်းမှာ V1 အောင်မြင်မှု တုံ့ပြန်မှု လိုအပ်ချက် `200`. ဖောက်သည်များက အခြား အောင်မြင်မှုများကို ငြင်းပယ်ကြသည် `2xx` မမျှော်လင့်တဲ့ တုံ့ပြန်မှုအဖွဲ့ကို တုန့်ပြန်ခြင်းမရှိဘဲ သဘောတူစာချုပ်အနှောင့်အယှက်တစ်ခုအဖြစ် ကုဒ်များ client error တွေကြောင့်ပါ။ server က code ကိုဖြုတ်ချလိုက်တဲ့အခါပဲ `[A-Za-z0-9_.:-]{1,128}` နောက်ပြီး ခန္ဓာကိုယ်ပါဝင်မှု (သို့) တိုက်ခိုက်သူရွေးချယ်မှုကို တားဆီးတဲ့ တုံ့ပြန်မှု parser/validation အကြောင်းရင်းတွေကို ပစ်ချပါ။ JSON အကြောင်းပြချက်သိမှတ်မှု မှတ်တမ်းတွေကနေ ပြန်ပေါ်လာတဲ့ နယ်မြေအမည်တွေပါ။

## ကျရှုံးမှုနှင့် ပြန်လည်ထူထောင်ခြင်း {#failure-and-recovery}

မလုံလောက်တဲ့ (သို့) ခေတ်နောက်ကျနေတဲ့ စာရင်းစစ်သူ အတည်ပြုချက်တွေ၊ သုံးခုထက်မနည်းသော validator မဲများ၊ မှားယွင်းတဲ့ အမြစ်တွေ (သို့မဟုတ်) ရာသီဥတုများ၊ duplicate nullifiers, အစားထိုးထားတဲ့ အထောက်အထား (သို့) capsules တွေ၊ တရားဝင်မဟုတ်တဲ့ ငွေကြေး ငွေလွှဲပြောင်းမှု အပိုင်းအခြား၊ သက်တမ်းကုန်ဆုံးနေတဲ့ ဘက်ဒယ်များနဲ့ မညီမျှတဲ့ ပြန်ဆပ်နှုန်း သတ်မှတ်ချက်တွေဟာ ကမ္ဘာလုံးဆိုင်ရာ ဗီဇပြောင်းလဲခြင်းမတိုင်ခင် ကျရှုံးသွားပါတယ်။ သဘောတူညီချက် နောက်ဆုံးသတ်မှတ်ချက်တွေက ဘယ်တော့မှ ပုဂ္ဂလိကပြည်နယ်ကို ပြောင်းလဲတာမဟုတ်ဘူး။

အတည်ပြုသူများသည် sidecar များ၊ အဆင့်လိုက် delta များနှင့် အဆင့်လက်မှတ်များကို အသိအမှတ်မပြုမီ fsync လုပ်သည်။ ပြန်လည်စတင်ရာတွင် စံသတ်မှတ်ထားသော အမြဲတမ်းမှတ်တမ်းများမှ reservation များကို ပြန်လည်တည်ဆောက်ပြီး၊ ထို့နောက် မပြောင်းလဲနိုင်သော ကမ္ဘာလုံးဆိုင်ရာ ရလဒ်မှတ်တမ်းများ၊ abort marker များ သို့မဟုတ် သက်တမ်းကုန်ဆုံးမှုနှင့် ညှိနှိုင်းသည်။ ကြီးကြပ်ထားသော reconciler သည် ညှိနှိုင်းရန် terminal candidate မရှိသည့်အခါတွင်ပင် တစ်ပြိုင်တည်းမြင်ထားသော အာဏာပိုင် height တွင် terminal retention pruning ကို လုပ်ဆောင်ပြီး၊ pruning အမှားဖြစ်ပါက လုံခြုံစွာ ပယ်ချသည်။ အာဏာပိုင် ကမ္ဘာလုံးဆိုင်ရာ terminal record သာ staged lock များကို ဖြေလွှတ်သည်။ အပြီးသတ်ရလဒ်မှတ်တမ်းအတိအကျကို ပြန်လည်တင်သွင်းခြင်းနှင့် ပဋိပက္ခဖြစ်သော ပြန်လည်တင်သွင်းခြင်း နှစ်ခုစလုံးကို အခြေအနေမပြောင်းဘဲ သတ်မှတ်ချက်တကျ ပယ်ချသည်။

ကြိုတင်သတ်မှတ်မှု အမှတ်အသား သည်အပြည့်အစုံသောလမ်းကြောင်းကိုပါ ၀ င်သည်။ ပရိုတိုကော data group head များသည် `(route, pool_id, epoch, root)` ကိုအသုံးပြုသည်၊ nullifiers သည် `(route, pool_id, nullifier)` ကိုအသုံးပြုသည်နှင့် output များသည် `(route, pool_id, commitment)` ကိုသုံးသည်။ အခြားလမ်းကြောင်းတွင်တူညီသည့် opaque တန်ဖိုးများသည် သီးခြားဖြစ်သည်၊ အတိအကျလမ်းကြောင်းတိုက်ခိုက်မှုသည် restart တွင်ပိတ်ထားသည်။

Operational alerts များတွင် opaque bundle, route, phase, cryptographic digest value, height နှင့် reason-class fields များသာ အသုံးပြုသင့်သည်။ logs, events, metrics labels သို့မဟုတ် tracing spans များတွင် ဘယ်တော့မှ decrypted capsules, အကောင့် သို့မဟုတ် ပိုင်ဆိုင်မှု အမှတ်အသားများ, amounts, memos, view data, proof witnesses, သို့မဟုတ် ခွဲခြမ်းဖတ်ရှုကိရိယာ payload များကို ထည့်မထားပါနဲ့။

## အစစ်တန်ဖိုးမတိုင်မီ အရည်အသွေး {#qualification-before-real-value}

သင်ဖြန့်ချိဖို့ရည်ရွယ်တဲ့ တိကျတဲ့ build နဲ့ configuration အတွက် အောက်ပါအချက်အလက်တွေကို ဖုံးအုပ်ထားပါ။

- ပဋိပက္ခသက်သေ၊ ကပ်ဆူလ်၊ မူဝါဒ၊ သော့လှည့်ခြင်း၊ ပြန်လည်ပေးချေခြင်းနှင့် ပြန်လည်ဖြည့်စွက်မှု ကိစ္စများ
- validator နှင့် coordinator ပြန်လည်စတင်ခြင်းအပါအဝင် 2, 3, 4, 8 နှင့် 16 ဒေတာဘေ့စ်များအတွက်စစ်မှန်သော ၄-validator လုပ်ငန်းစဉ်များ၊ စစ်ဆေးထားသော ၅%, ၁၀% နှင့် ၂၀% သတင်းစကားဆုံးရှုံးမှု၊ အဆင့်ပိုင်းခြားခြင်း၊ ပြန်လည်ထူထောင်ခြင်းနှင့် persistence ကန့်သတ်မှု ပျက်စီးမှုများ။
- Torii, P2P, blocks, Kura, point-in-time data views, queries, events, logs, နှင့် တယ်လီမက်ထရီ အကြားက ကန်နာရီနှင့်ကွဲပြားခြားနားသောသွေးလျှံမှုလေ့လာချက်များ
- အနည်းဆုံးအပူချိန်ငါးခုနှင့် real network ပါဝင်သူအရေအတွက်ကို တိုင်းတာမှုသုံးဆယ်စုပေါင်း, p50, p95, p99, ယုံကြည်မှု ကြားကာလများ, အရင်းအမြစ်များ, ယာဉ်မောင်းနှင်မှု၊ သက်သေခံချက်နှင့်ပရိုတိုကောလစ်ရလဒ်မှတ်တမ်းအရွယ်အစားများ, နှင့် ပွင့်လင်းမြင်သာသော AMX ကိုထိန်းချုပ်ခြင်း
- ကျဉ်းမြောင်းတဲ့ အလုပ်ခွင် စမ်းသပ်မှုများ၊ lint နှင့် ဖွဲ့စည်းချက် စစ်ဆေးမှုများ၊ ကြုံရာမျိုးစေ့များ၊ စုပ်ယူခြင်း၊ ပြန်လည်ဖန်တီးနိုင်သော builds SBOMs များနှင့် လက်မှတ်ထိုးထားသော artefact cryptographic hashes များ
- တရားဝင် အလွှာ နှစ်ခုစလုံး: ၃/၂၅၅ ခြေထောက်ရေတွက်မှုအချိုးအစား စစ်ဆေးချက်များနှင့် မှန်ကန်သော ၄-validator ကော်မတီစာရင်း N=2 validator-focused အပြည့်အဝသတ်မှတ်ထားသောအမှား၊ စက္ကူ-ပထမဦးဆုံး N=3 မှားယွင်းမှု၊ N=4 clean နှင့် N=3 expiry/replay configurations များ၊ အမှားဘတ်ဂျက်များကိုကော်မတီတစ်ခုစီအတွက် လွတ်လပ်စွာပြုလုပ်သည်။
- အတည်ပြုမှု ဆက်ဆံရေး၊ dummy-slot ရွေးချယ်သူတွေ၊ အရင်းအမြစ်နဲ့ ကပ်ဆူလ် ချည်နှောင်မှု၊ ပြန်လည်ဖြည့်စွက်မှု ဆက်စပ်မှု, လျှို့ဝှက်ဆန်းကြယ်မှုနဲ့ cross-data space state machine တွေကို လွတ်လပ်စွာ စစ်ဆေးပါ။

ရိုးရိုးနှင့် သန့်စင်ထားသော အထောက်အထားများ၊ ခြိမ်းခြောက်မှုပုံစံများ၊ ပရိုတိုကော ဆွေးနွေးချက်များ၊ ကန့်သတ်ချက်များ၊ အရင်းအမြစ်ကုဒ် ပြင်ဆင်ရေး ID များ၊ ဆော့ဝဲ သရုပ်ဖော်ချက်များ နှင့် စစ်ဆေးမှု အစီရင်ခံစာများကို မပြောင်းလဲနိုင်သော DOI ထောက်ပံ့ထားတဲ့ လက်ရာပစ္စည်း။ မှတ်ပုံတင် စမ်းသပ်မှုတစ်ခုတည်းက ဒီ feature ကို ထုတ်လုပ်မှု အရည်အချင်းရှိတဲ့ CBDC ငွေကြေးငွေပေးချေမှု စနစ်အဖြစ် မပြောင်းဘူး။

နောက်ဆုံးရှင်းလင်းတဲ့ Iroha checkout ကနေ လွတ်မြောက်မှု အရင်းအမြစ် စာရင်းကို ဖန်တီးပြီး အဲဒီ checkout အပြင်မှာ ရှိပြီးသား bundle root ကို တံဆိပ်ခတ်ပါ။

```sh
python3 scripts/private_settlement_source_evidence.py \
  --repository-root . \
  --bundle-root /absolute/path/to/release-bundle
```

ထုတ်လုပ်သူက ရိုက်ကူးမှုအတွင်းမှာ ပွဲတင်ထားတဲ့၊ ပွဲတင်မထားတဲ့၊ ခြေရာခံမထားတဲ့ (သို့) ပေါင်းစပ်မထားတဲ့ ဖိုင်တွေနဲ့ အရင်းအမြစ်ပြောင်းတာတွေကို ကျရှုံးစေတယ်။ ၎င်းသည် raw source-code revision object ကို ထိန်းသိမ်းထားပြီး single protocol-standard Git tree inventory, တိကျတဲ့ binary path list, deterministic source seal နဲ့ `Cargo.lock`; လက်ရာထုတ်ပြန်ချက်တိုင်းကို ၎င်းရဲ့ JSON နောက်ဆုံးထုတ်ပြန်မှုဆိုင်ရာ အထောက်အထားကို ထုတ်ပေးသည်။ DOI- အစုအဝေး စစ်ဆေးသူ (သို့) ပြင်ပ ထုတ်လွှတ်မှုဂိတ်တစ်ခုခု။

အရင်းအမြစ် တံဆိပ်ဟာ သယ်ဆောင်နိုင်ပြီး ပိတ်ထားခြင်းမရှိပါ။ ထုတ်လုပ်သူနဲ့ နောက်ဆုံး စစ်ဆေးသူက သိမ်းဆည်းထားတဲ့ symlink graph တစ်ခုလုံးကို ဖြေရှင်းပေးတယ်၊ ဒီတော့ root ထဲမှာ ပေါ်ပေါက်ပေမဲ့ အခြား link တစ်ခု၊ စက်ဝန်းတစ်ခု၊ `.git` ဖြတ်သန်းမှု (သို့) Windows ပုံစံ ရည်မှန်းချက်တစ်ခုကနေ လွတ်မြောက်တဲ့ link ကို link တွေမဖန်တီးခင် ပယ်ချပါတယ်။ Structured source နဲ့ gate reports တွေကို cryptographic digest value နဲ့ length က release technical manifest နဲ့ ကိုက်ညီတဲ့ bounded stable files တွေကနေပဲ parsed လုပ်ထားပြီး source payload အမျိုးအစားတိုင်းဟာ တစ်ကြိမ်သာ ဖြစ်ပေါ်ရပါမယ်။

မူရင်း ချို့ယွင်းမှု စမ်းသပ်လည်ပတ်မှု နှင့် latency နမူနာတိုင်းသည် release source code revision အပြည့်အဝ၊ တည်ဆောက်ထားသော pinned hardware description တစ်ခု၏ SHA-256 ကိုနှင့် ၎င်းရဲ့ တိကျတဲ့ ပါဝင်သူအရေအတွက် သတ်မှတ်ချက် ၏ SHA-256 ကို ချိတ်ဆက်ပေးရမည်။ N=2,3,4,8,16 ကိုဖုံးအုပ်ထားသော ပရိုတိုကုတ်စံညွှန်း ဖွဲ့စည်းမှု နည်းပညာထုတ်ပြန်ချက် တစ်ခုကို သိမ်းဆည်းပါ။ စာရင်းတစ်ခုစီမှာ ထိန်းသိမ်းထားသည့် ဖွဲ့စည်းရေး ဘိုက်များကို ရည်ညွှန်းပြီး ဒေတာနေရာတစ်ခုအတွက် အတည်ပြုသူ ၄ ဦးတိတိကျမှန်ကန်ကန်၊ ၃-of-4 ကော်မတီနှင့် RS16 DA/RBC ကို လက်မှတ်ထိုးရန်လိုအပ်သည်။ အဆိုပါ ဖြန့်ချိမှု စစ်ဆေးကိရိယာ သည်အခြား build၊ စက်ပစ္စည်း ပရိုဖိုင် သို့မဟုတ် ကွန်ရက် သတ်မှတ်ချက် များပေါ်တွင်ထုတ်လုပ်သော summaries ကိုပယ်ဖျက်သည်။ တစ်ဦးချင်းဆုံးရှုံးမှု, phase-cut နှင့် persistence-crash အတန်းတိုင်းသည် SHA-256 -bound အတွင်းမှာကမ္ဘာလုံးအရပြန်လည်အသုံးပြုမည့် တိကျသော JSONL မှတ်တမ်းညွှန်ကြားချက်များကိုလည်းအမည်ပေးရမည်ဖြစ်သည်။ authenticated-controller နဲ့ atomicity-capture artefacts တွေ။ ဖြန့်ချိမှု စစ်ဆေးကိရိယာ က အဲဒီ cryptographic digests တွေကို ဖြေရှင်းပေးပြီး row တွေဟာ စမ်းသပ်လည်ပတ်မှု အမှတ်အသား, trial index နဲ့ parameters တွေ၊ ထိန်းချုပ်ကိရိယာ အသိအမှတ်ပြုချက် သို့မဟုတ် ပြန်လည်ရယူမှု ရလဒ် တွေနဲ့ ဆက်တိုက် စစ်ဆေးတဲ့ count ကို လိုက်ဖက်အောင် လုပ်ဖို့ လိုအပ်ပါတယ်။ နောက်ပိုင်းထုတ်ဝေမှု p95/p99 နှိုင်းယှဉ်ချက်များသည်လည်း လက်မှတ်ရေးထိုးထားသော အခြေခံအဆင့်ကို ပယ်ချသည်၊ ၎င်း၏ Hardware, Configurations သို့မဟုတ် တိုင်းတာမှုလိုအပ်ချက်များက ပြိုင်ဘက်နှင့် ကွဲပြားသည်။ နောက်ဆုံးစစ်ဆေးသူသည် မှတ်တမ်းတင်ထားသော မူကြမ်းနမူနာများမှ သတင်းထုတ်ပြန်သည့် ရာခိုင်နှုန်းအားလုံး၊ MADs နှင့် သတ်မှတ်ချက်ဆိုင်ရာ ယုံကြည်မှု ကြားကာလများကို သီးခြားချိတ်ဆက်ထားသော စိစစ်ချက်စုဆောင်းချက်အပေါ် မှီခိုခြင်းအစား ပြန်လည်ပြုပြင်သည်။ အလားတူပဲ Canary Technical Manifesto ကို ပြန်လည်ထည့်သွင်းပြီး မှတ်တမ်းတင်ထားတဲ့ ပုဂ္ဂလိကရေးရာ မျက်နှာပြင်တိုင်းကို လွတ်လပ်စွာ စကင်ဖတ်တယ်၊ ဒီတော့ အစီရင်ခံစာတစ်ခုဟာ ဖိုင်က cryptographic digests တွေကို ပြန်လည် ချိတ်ဆက်ပြီးနောက် ပျိုးထားတဲ့ လျှို့ဝှက် hit ကို ဖိနှိပ်လို့မရဘူး။ လျှို့ဝှက်သာ run တစ်ခုစီမှာ ပိုင်ရှင်တစ်ဦးတည်းရဲ့ unfiltered loopback pcap၊ raw tcpdump stderr နဲ့ zero-drop စာရင်းအင်းတွေ၊ Single Protocol Standard Port Technical Manifesto တွေ၊ packaged restricted source archive တွေနဲ့ အဆင့်တူကွန်ရက် အက်တမ်မကွဲနိုင်မှု observation တွေကို သိမ်းထားရမှာပါ။ နောက်ဆုံး စစ်ဆေးသူသည် ထုတ်ဝေသော အကျဉ်းချုပ်ချက်များကို ယုံကြည်ခြင်းထက် ထို archived bytes များမှ port bound packet split၊ source projections နှင့် baseline-to-terminal atomicity checks တို့ကို ပြန်လည်ထုတ်ပြန်သည်။

လက်ဝဲနှင့်ညာ ဖိုင်လမ်းကြောင်းများ၊ အမျိုးအစားများ၊ ဘိုက်တာအလျားများနှင့် လိုအပ်သော သီးခြားလွတ်လပ်ရေးမျက်နှာပြင်တစ်ခုစီအတွက် SHA-256 cryptographic digests များကို ချိတ်ဆက်ပေးသည့် တစ်ခုတည်းသော ပရိုတိုကောစံညွှန်းစုံတွဲ Traffic-count နှင့် Differential-pair နည်းပညာ manifest များလည်း ပါဝင်ရမည်ဖြစ်သည်။ ၎င်း၏ ကြေညာထားသော အမြစ်များတွင် စုံတွဲ archival inventory ကိုတိကျစွာပါဝင်ရမည်ဖြစ်သည်။ စစ်ဆေးသူသည် သာမန်မျက်နှာပြင်များအတွက် တူညီသော file အရွယ်အစားများနှင့် JSON အများပြည်သူပုံစံများကိုလိုအပ်သည်။ entropy ပါတဲ့ raw loopback capture နဲ့ packed restricted-source archive တို့ဟာ တိကျတဲ့ အရွယ်အစား ခြွင်းချက်တွေပါ၊ ဒီအစား packet link အမျိုးအစားနဲ့ packet တစ်ခုချင်းအလျား၊ ကန့်သတ်ထားသော အရင်းအမြစ် အမှတ်အသားများ နဲ့ fixed-shape row length တွေကို နှိုင်းယှဉ်တယ်။ Torii request/response, public/restricted P2P packet, block, query, event, log, နှင့် တယ်လီမက်ထရီ လမ်းကြောင်းအရေအတွက် ကိုလည်း လိုက်ဖက်အောင် လုပ်ရပါမယ်။ သို့မဟုတ် အတွဲမရှိသော ဖိုင် ကို leakage report နဲ့ its cryptographic hash တွေကို ပြန်ရေးသားပြီး ဖုံးကွယ်လို့မရဘူး။
