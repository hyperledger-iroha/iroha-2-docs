# アトミックなプライベートクロスデータスペースの金融取引決済を実行する {#run-atomic-private-cross-dataspace-settlement}

`AtomicPrivateSettlementV1` は、2 から 255 の SORA Nexus データスペースのそれぞれで機密の財務送金パートを調整し、すべての財務送金パートを 1 つのグローバル状態で確定します取引。拒否された、期限切れの、または中止されたバンドルは、金銭的な移転部分を適用しません。透明なネイティブ AMX DvP/PvP は別のプロトコル経路として残ります。

::: warning リリース状況
この機能は管理されており、デフォルトでは無効であり、まだ本番用には適格ではありません。公開された機能が利用可能になるまでは、実際の CBDC 値で有効にしないでください。プライバシー、障害、パフォーマンス、再現可能ビルド、独立暗号レビュー、および成果物公開のゲートは、すべて正確なリリースに対して通過しました。
:::

## プロトコルが隠しているもの {#what-the-protocol-hides}

各金融送金パートは、固定された二入力三出力のプライベートノート証明を使用します。委員会の検証者は、証明と不透明な状態遷移を検証しますが、平文の当事者、資産、金額、メモ、またはビジネス結果は受け取りません。認可された現地の監査人は、パディングされた監査カプセルを復号し、その内容を確認し、目的ごとに分離された承認に署名します。デフォルトのポリシーでは、管理対象の監査人セットからの1つの承認を受け入れます。

公開コンテナ取引およびプロトコル結果記録は、意図的に以下を明らかにする：

- ネットワークおよびバンドル識別子
- 参加者データスペースルートと参加者数
- タイミングと有効期限の高さ
- 安定した不透明なプロトコルデータグループ識別子、ルート、ヌリファイアー、暗号コミットメント値、および固定暗号文スロット
- 委員会の承認原則および正確な3分の4の可用性、準備、ならびにプロトコル確定証明書
- スポンサー、パブリックネットワーク料金、端末の状態

これはコンテンツの機密性であり、トラフィックフローの匿名性ではありません。タイミング、参加者の数、データスペースの識別、および安定プールの活動は公開されたままです。1つの CBDC のみをホストするデータスペースも、リテラルな資産識別子が公開されていなくても、ルートから資産を推測できる場合があります。

各固定暗号化出力は、その認可された使い捨て出力ビューキーから派生した `recipient`識別子を公開します。1つの金融送金部分にある3つの識別子は異なるものでなければなりません。完全なPrepareバリアおよびプロトコル結果記録は、そのチェックをすべての金融送金部分に拡張します。投票準備の前に、各委員会のバリデーターは、確定済みの WSV にすでに存在する識別子も拒否します。グローバルな確定は、確定済みバンドルの履歴全体にわたり、決定論的な受信者インデックスと同じルールを適用します。インデックスはデータスナップショットのペイロードから除外され、復元時には標準化された暗号化出力から再構築されるため、永続的な重複はクローズ状態で失敗します。これは一回限りの識別子であり、リプレイ境界です。公開前に悪意のある送信者やネットワーク監視者がトラフィックを関連付けられないことを保証するものではありません。

## 展開要件 {#deployment-requirements}

起動前に、オペレーターは次のすべてを必要とします:

1. 参加している各データスペースごとに正確に4つのバリデータが存在し、それぞれ異なる BLS コンセンサスキーと所持証明を持つ
2. すべての高さで必須 Sumeragi DA/RBC が有効
3. すべてのデータスペースにおける、管理された機密金融取引清算プロトコルデータグループおよび初期ルート
4. アクティブな V1 プライベートノート機能と、別個の金融取引決済証明プロファイル
5. 少なくとも1つの管理されているローカル`PrivateSettlementAuditPolicyV1`、これには異なる監査人の署名やハイブリッド暗号鍵、鍵のエポック、高さの有効性、および承認閾値が含まれます
6. 設定された保持期間のための十分なプライベート補助記録ストレージ
7. 最終的な公開コンテナ取引を提出できる中立的なスポンサーアカウント

監査人はバリデーターを操作することもできますが、別々のコンセンサス、監査人署名、および監査人暗号化キーを使用しなければなりません。廃止された復号キーは規制上の保存期間中保持するか、廃止する前にカプセルの再暗号化を管理・テストしてください。

四検証者認証の原則はクライアントによって提供されるのではなく、状態に依拠しています。技術マニフェストの`authority_context_height`において、各検証者はコンセンサス状態から正確な順序付きレーン/データスペースの名簿およびアクティブな実行レーンの化身を解決し、解決された高さが一致することを要求します。そして4つの BLS キーと所持の証明を確認します。アップロード、準備、および最終プロトコル結果記録の承認はすべて同じ歴史的認可原則を使用します。

Prepareバリア、最終プロトコル最終化バンドル、およびプロトコル結果記録は、1つのコンパクトな二層認可主体カタログを共有します。それの`rosters`にはルートフリーのバリデータIDと整列された BLS 所有証明が含まれており、正準の初回使用順で重複排除されています。`leg_roster_indices[i]` は技術的マニフェスト財務転送部分 `i` のロスターを選択します。フェーズ証明書の `authority_catalog_index` は、ロスターインデックスではなく、論理的なマニフェスト処理順序のままです。権限の消化または QC の検証の前に、バリデーターは、その技術的なマニフェストの財務転送部分の正確な経路とアクティブな実行レーンの具現化を選択された名簿と組み合わせて、経路に結び付けられた`PrivateSettlementCommitteeAuthorityV1`を再構築します。

## 入場を設定する {#configure-admission}

すべての生産動作はノードの設定から生じます。環境変数ではこのパスを有効化できません。出荷時のデフォルトは `enabled = false` です；機能を無効のままにするには、特定の処理区分の設定は不要です。

ガバナンスが必要な機能を登録し、十分な通知とともに有効化高さを選択した後、すべての関連ノードを一貫して設定します:

```toml
[nexus.atomic_private_settlement]
enabled = true
activation_height = 500000
minimum_activation_notice_blocks = 7200
proof_profile_version = 1
max_participants = 255
max_expiry_blocks = 7200
audit_timeout_blocks = 1200
prepare_timeout_blocks = 1200
commit_timeout_blocks = 1200
capsule_padding_classes_bytes = [4096, 16384, 65536, 262144]
max_proof_bytes = 8388608
max_capsule_bytes = 1048576
max_carrier_bytes = 4194304
sidecar_retention_blocks = 1000000
sidecar_max_records = 256
sidecar_max_total_bytes = 3221225472
default_min_auditor_approvals = 1
permitted_policy_versions = [1]
```

この例では、出荷された V1 の制限を使用しており、性能推奨ではありません。ストレージ、プルーフ、カプセル、コンテナトランザクション、およびレイテンシデータコンテナを測定します。動作範囲を選択する前に、意図したハードウェアを確認してください。三相のタイムアウトは`max_expiry_blocks`内に収まる必要があり、補助記録の保持期間は少なくともその有効期限の期間でなければなりません。

`max_capsule_bytes` は、全体の `PrivateSettlementAuditCapsuleV1` の正規の Norito エンコーディングを制限します: AAD、暗号用ノンス値、暗号文、ベクターフレーミング、監査者の識別情報、およびすべてのラップされた DEK 行。それは、暗号文のみの制限ではありません。各構成されたパディングクラスは、少なくとも`default_min_auditor_approvals`人の監査人にとって保守的な全カプセルデータコンテナに適合しなければなりません。Torii はまた、`min_approvals`がその規制下の下の新規承認ポリシーを拒否し、完全な正準符号化が大きすぎる実際のカプセルも拒否します。

`max_carrier_bytes` は、認定バンドルだけでなく、完全な正規スポンサー署名付きトランザクションを制限します。この件数には、登録済みの指示フレーミングも含まれます。トランザクション承認の主体とメタデータ、手数料の意図、そして署名。通常のネットワークトランザクションの制限は、独立した上限として依然として適用されます。

統御される能力がアクティブであり、その状態と有効化高さが通知期間を満たし、コンパイルされた証明プロファイルが V1 と一致し、オンチェーンのプロトコルデータグループおよび監査記録が最新である場合を除き、アクティベーションはクローズ状態で失敗します。構成フラグを有効にするだけでは不十分です。

## 金融取引決済ワークフロー {#settlement-workflow}

クライアントは証明と暗号化カプセルをローカルで作成します。秘密の証人はネイティブウォレットまたはネイティブワーカー内に保持する必要があり、アプリケーションログ、Python オブジェクト、HTTP リクエスト、または永続的なコーディネーションレコードにシリアライズしてはいけません。

カプセルおよび監査人ごとの DEK-ラップ認証データには、正確な状態に基づく委員会および `authority_context_height` の暗号学的ダイジェスト値、ならびにネットワーク、ルート/化身が含まれます、バンドル、金融転送部分、ポリシー、重要な時代、平文の暗号コミットメント値。ラップされたキーは、異なる名簿や履歴的認可プリンシパルのコンテキストに移動することはできません。

各標準的な財務送金部分について、コーディネーターは次にこの手順を実行します：

1. 暫定的な暗号化資料を4つのすべてのバリデータにアップロードし、正確な3分の4の可用性証明書を取得してください。
2. 以下に説明する認証済みの `POST` リクエストを使用して、公認監査人にカプセルを取得させ、復号し、公開バインディングを再計算し、ローカルポリシーを適用し、承認を提出させてください。ポリシーの回転後のカプセルアクセスは保持専用です：現在の後継者は適格な過去の読み取りを許可できますが、古いポリシーの下で準備された金融転送パートに承認を追加することはできません。
3. 四人のバリデーターからの準備投票を要求します。各バリデーターは独立してデルタを検証し、投票前に確実にステージします。ステージされた各レスポンダーに、標準の3対4の準備証明書を永続化します。
4. すべての決済区間について Prepare 証明書がそろったら、変更不能な完全 Prepare バリアを構築します。標準形式の 3-of-4 Commit 証明書を要求して永続化します。コーディネーターが再起動した場合は、参加ノードにローカルで永続化された Prepare 証明書と Commit 証明書を照会し、標準形式でクォーラムと同等の証明書を選択して、処理を続行する前に再配布します。認証されていないローカルキャッシュから証明書を再構築してはいけません。
5. 技術マニフェストのスポンサーに署名させ、正確に1つのグローバルコンテナ取引を提出させてください。コンテナ取引には1つの `FinalizeAtomicPrivateSettlementV1` 指示と、完全に認定されたバンドルが含まれています。コーディネーターと WSV は、登録済みの指示フレーミングを含む、完全な型消去済みの最終化指示を事前に計測します。Torii とコアのワンショットコンテナ取引バインディングは、正確な標準的なスポンサー署名付き取引に対して`max_carrier_bytes`を強制します。承認主体、メタデータ、手数料意図、署名を含む。Torii は、承認主体のコンテキストの前、最終確定に達し得る最後の入力高さ以降、または管理される有効期限の期間を超えた場合にコンテナトランザクションを拒否します。
6. グローバル最終性が得られるまで、公開バンドルの状態とプロトコル結果記録を照会してください。ローカル補助記録の状態は、その不変のグローバル最終記録と照合されるまで暫定的なものとして扱ってください。

Rust クライアントは、このフローを `certify_and_upload_private_settlement_legs_v1`、`prepare_private_settlement_bundle_v1`、`commit_private_settlement_bundle_v1`、および `submit_private_settlement_bundle_v1` を含むメソッドを通じて公開します。再起動に安全な調整には `recover_or_prepare_private_settlement_bundle_v1` および `recover_or_commit_private_settlement_bundle_v1` を使用します。委員会および監査人の技術的呼び出しには明示的な役割資格情報が必要であり、通常のアカウント暗号署名者を再利用することはありません。

## 監査ポリシーを安全にローテーションする {#rotate-an-auditor-policy-safely}

プライバシーガバナンス認可済み`RotatePrivateSettlementPoolPolicyV1`指示を使用してください。正確な現在のガバナンス暗号化ダイジェスト値を指定し、同じルート、プロトコルデータグループ、および資産紐付け暗号化コミットメント値を保持し、ガバナンスの改訂を1つ進める必要があります。厳密に新しいキーエポックと異なるポリシー／ガバナンス暗号ダイジェストを使用し、ローテーションを含むブロックで有効化します。プロトコルデータグループのフロンティア、ルート、ヌリファイア、出力、リプレイセットおよび確定されたプロトコル結果記録は保存されます。その回転の有効化高さで同じルート/プールに触れるプロトコル結果記録を含めないでください。その指示はその境界を拒否します。

公開プロトコルデータグループの予測は、完全な置き換えられたポリシー改訂の系譜を保持します。したがって、ローテーション前に確定されたプロトコル結果記録は、再起動後も歴史的証拠として有効なままです。その正確なプロトコル結果レコードを再生すると、状態変更なしに決定的に拒否されます。系統は未完成の作業を認可しません：活性化の境界を越える古いポリシーバンドルは、グローバル状態が変更される前に閉じた状態で失敗します。後続のポリシーは、後のガバナンス改訂およびキーエポックと同じポリシー系統に属している場合にのみ、保持された履歴カプセルの読み取りを許可できます。そして、認証された現在の署名キーは、履歴ポリシーおよびラップされた-DEK 名簿において同じ安定した監査人の識別情報に対応します。カプセルは履歴監査人キーに対して暗号化されたままです:それを開くためには、正確な歴史的復号キーを保持するか、キーを破棄する前に管理され、テストされたカプセルの再包装を完了する必要があります。この保持アクセスは、回転された/現在のポリシーが古い準備済みポリシーの下で承認を追加することを許可するものではありません。

## Torii ルートファミリー {#torii-route-family}

これらのルートは標準の Norito リクエストおよびレスポンスオブジェクトを使用します。認証済みおよび制限付きのレスポンスはプライベートな`no-store`キャッシュ動作を使用します。

|操作|方法と経路|校長|
| ------------------ | -------------------------------------------------------------------------- | --------------------------- |
|財務転送部分をアップロード| `POST /v1/nexus/private-settlements/legs`                                  |標準的なアカウント署名|
|利用可能性の共有|`POST /v1/nexus/private-settlements/legs/availability-shares`|標準的なアカウント署名|
|投票の準備をする|`POST /v1/nexus/private-settlements/phases/prepare-votes`|標準的なアカウント署名|
|最終段階の投票| `POST /v1/nexus/private-settlements/phases/commit-votes`                   |標準的なアカウント署名|
|持続フェーズ QC| `POST /v1/nexus/private-settlements/phases/certificates`                   |標準的なアカウント署名|
|回復フェーズ QCs| `GET /v1/nexus/private-settlements/legs/{payload_digest}/phase-certificates` |技術的マニフェストスポンサー|
|金融送金の部分ステータス| `GET /v1/nexus/private-settlements/legs/{payload_digest}/status`           |標準的なアカウント署名|
|委員会校正|`GET /v1/nexus/private-settlements/legs/{payload_digest}/committee-proof`|正確なロスター検証ツール|
|監査カプセル| `POST /v1/nexus/private-settlements/legs/{payload_digest}/audit-capsule`   |管理された監査人|
|監査人の承認| `POST /v1/nexus/private-settlements/legs/{payload_digest}/audit-approvals` |管理された監査人|
|最終送信／中止| `POST /v1/nexus/private-settlements/bundles`                               |技術的マニフェストスポンサー|
|バンドルのステータス|`GET /v1/nexus/private-settlements/bundles/{bundle_id}`|パブリック|
|プロトコル結果記録または中止|`GET /v1/nexus/private-settlements/bundles/{bundle_id}/receipt`|パブリック|

公開状態およびプロトコル結果記録 APIs は、文書化された公開フィールドのみを公開します。特に、通常の資金移動部分の状態は承認を明らかにしませんカウントまたは管理対象オーディタしきい値。制限付き読み取りは、意図的に欠落、許可されていない、期限切れの資料を同じ利用不可応答クラスに統合します。

監査カプセル操作は読み取り専用で、IDに紐付けられた `POST` であり、`GET` ではありません。その署名付き Norito JSON リクエスト本体は正確に `{"audit_policy": <PrivateSettlementAuditPolicyV1>}` です：現在の完全な管理ポリシーが認可の証拠であり、クライアント提供の認可主体ではありません。ノードはカプセルの履歴 `audit_policy` を技術マニフェストの `authority_context_height` で有効なガバナンス改訂にバインドし、要求された現在または後続のポリシーをノード権限読み取り高さで有効な改訂にバインドします。そして、認証された署名キーを、両方のポリシーで共有される安定した監査者のIDを通じてマッピングします。認証された応答は、過去の`audit_policy`を反映します、そしてアクセスに使用される正確なポリシーは `access_audit_policy` として使用され、レスポンダーの証明は両方を拘束します。クライアントは、`access_audit_policy` がリクエストで送信されたポリシーと等しくなることを要求する必要があります。

提出ルートは、正確に1件の直接のスポンサー署名付き最終化または中止指示のみを受け付けます。その`202`応答には、バンドルID、観測された受理高さ、およびコンテナ取引の暗号ハッシュのみが含まれます。キューに入れられた中止がすでに最終であると主張するものではありません。 SDKs は両方の識別子が正規のチェックサム付き Norito `Hash` JSON リテラルであり、高さが正確な符号なし64ビット整数であることを要求します。欠落、追加、誤記、正規でない、チェックサム無効、負、負のゼロ、小数、またはオーバーフローしたフィールドは閉塞失敗になります。権威ある端末状態にはバンドルステータスまたはプロトコル結果レコードを使用してください。ステータスコードも正確です：このコンテナの取引受け入れルートには`202`が必要ですが、その他のすべてのプライベート決済 V1 の成功レスポンスには`200`が必要です。クライアントは、予期しないレスポンスボディをクライアントエラーで反映することなく、契約の逸脱として代替の成功した`2xx`コードを拒否します。彼らはサーバー拒否コードのみを公開しますそれが`[A-Za-z0-9_.:-]{1,128}`と一致したとき、応答パーサー/検証の原因を破棄し、ボディコンテンツや攻撃者が選んだ JSON フィールド名が原因認識ログを通じて再出現するのを防ぎます。

## 失敗と回復 {#failure-and-recovery}

監査人の承認が欠落しているか古いもの、3つ未満の検証者投票、誤ったルートやエポック、重複するヌリファイア、置き換えられた証明やカプセル、非正規の金融部品の注文の転送、期限切れのバンドル、および不一致の払い戻し条件はすべて、グローバル変異の前に失敗します。コンセンサス確定証明書は、決してプライベート状態を変異させません。

検証者は、補助レコード、ステージングされたデルタ、およびフェーズ証明書を確認する前に fsync します。再起動時には、正準耐久レコードから予約を再構築し、その後、不変のグローバルプロトコル結果レコード、中止マーカー、または有効期限を照合します。監督付きリコンシリエーターは、端末候補を調整する必要がない場合でも、同期的に観測された権威ある高さで端末保持の剪定を実行します。そして、プルーニングエラーで閉じた状態で失敗します。権限のあるグローバルターミナルレコードのみがステージされたロックを解放します。正確に最終化されたプロトコルの結果レコードの再生と、競合する再生はどちらも状態の変異なしに決定的に拒否されます。

予約識別子には完全なルートが含まれます。プロトコルデータグループのヘッダーは`(route, pool_id, epoch, root)`を使用し、ヌリファイアは`(route, pool_id, nullifier)`を使用し、出力は`(route, pool_id, commitment)`を使用します。別のルートでの等しい不透明値は独立しており、正確なルートの衝突は再起動後もロックされたままです。

運用アラートでは、不透明なバンドル、ルート、フェーズ、暗号ダイジェスト値、高さ、理由クラスのフィールドのみを使用する必要があります。復号されたカプセル、アカウントや資産の識別子、金額、メモ、ビューのデータ、証明の証人、またはパーサペイロードをログ、イベント、メトリクスラベル、またはトレーシングスパンに配置してはいけません。

## 実際の価値の前の資格 {#qualification-before-real-value}

展開する予定の正確なビルドと構成について、次の内容を網羅した証拠を記録してください:

- 対立証明、カプセル、ポリシー、キー回転、補償、およびリプレイのケース
- バリデータとコーディネーターの再起動、認証された5％、10％、20％のメッセージ損失、フェーズパーティション、回復、および永続境界クラッシュを含む、2、3、4、8、および16のデータスペースに対する実際の4バリデータプロセス
- カナリアおよび差分リーク分析を Torii、P2P、ブロック、Kura、データスナップショット、クエリ、イベント、ログ、テレメトリに渡って行う
- 実際のネットワーク参加者数ごとに少なくとも5回のウォームアップと30の測定済みバンドルを行い、p50、p95、p99、信頼区間、リソース、トラフィック、証明およびプロトコル結果の記録サイズ、および透明な AMX をコントロールとして
- 厳格なワークスペーステスト、リンとフォーマットのチェック、ランダム化されたシード、ソークテスト、再現可能なビルド、SBOMs、および署名付きアーティファクトの暗号ハッシュ
- 2 つの形式レイヤーの両方：3/255 区間の個数対称性チェックと、正確に 4 台のバリデータを使う委員会インデックス付き構成（N=2 のバリデータ重点構成と完全な有界障害構成、論文で主要対象とする N=3 障害構成、N=4 正常構成、N=3 有効期限切れ／リプレイ構成）。障害予算は委員会ごとに独立させます
- 証明関係、ダミースロットセレクタ、資産およびカプセルのバインディング、払い戻し関係、暗号化、およびクロスデータスペース状態機械の独立したレビュー

生の証拠と整理済みの証拠、脅威モデル、プロトコルの議論、制限事項、ソースコードの改訂ID、ハードウェアの説明、および監査報告書を公開する不変の DOI バックのアーティファクト。リポジトリのテストだけでは、この機能を本番対応の CBDC 金融取引決済システムにすることはできません。

最終クリーン Iroha チェックアウトから、リリースソースのインベントリを生成し、そのチェックアウト外の既存のバンドルルートに封入してください:

```sh
python3 scripts/private_settlement_source_evidence.py \
  --repository-root . \
```

プロデューサーは、ステージ済み、未ステージ、追跡されていない、またはマージされていないファイルや、キャプチャ中の任意のソース変更で失敗します。生のソースコードのリビジョンオブジェクト、標準化されたGitツリーインベントリ、正確なバイナリパスのリスト、決定論的なソースシール、および`Cargo.lock`を保持します；最終リリース技術マニフェストには、JSON の結果からのすべてのアーティファクト宣言を含めます。これは、最終的な DOI-バンドル検証者や外部リリースゲートを免除するものではありません。

ソースシールは携帯可能でフェイルクローズです：生産者と最終検証者はアーカイブされたシンボリックリンクのグラフ全体を解決するため、ルート内に存在するが他のリンクを通じて逃げるリンク、循環、`.git` のトラバーサル、または Windows スタイルのターゲットはリンクが作成される前に拒否されます。構造化されたソースおよびゲートレポートは、暗号ダイジェスト値と長さがリリース技術マニフェストと一致する限定された安定ファイルからのみ解析され、各ソースペイロードの種類は正確に一度だけ存在しなければなりません。

すべての生のフォールトランとレイテンシサンプルは、完全リリースのソースコードリビジョン、1つの構造化された固定ハードウェア記述の SHA-256、およびその正確な参加者数構成の SHA-256 に紐付けられなければなりません。N=2、3、4、8、16をカバーする1つの標準的な構成技術マニフェストをアーカイブしてください。各エントリは保持された構成バイトを参照し、各データスペースに対して正確に4つのバリデーター、3分の4クォーラム、および必須の署名 RS16 DA/RBC を主張する必要があります。リリース検証者は、異なるビルド、ハードウェアプロファイル、またはネットワーク構成で生成されたサマリーを拒否します。すべての個別の損失、フェーズカット、および永続クラッシュ行は、さらに SHA-256 に限定されたグローバルに再利用不可能な正確な JSONL レコード参照を指定する必要があります。認証コントローラーおよび原子性キャプチャのアーティファクト。リリース検証者はそれらの暗号学的ダイジェストを解決し、行が実行の識別、試行インデックスおよびパラメータ、コントローラーの確認または回復結果、連続チェックのカウントと一致することを要求します。そして部分的な可視性や使用可能性の観測はゼロです。後でリリースされるp95/p99の比較でも、ハードウェア、構成、または測定要件が候補と異なる署名済みのベースラインは却下されます。最終検証者は、切り離されたベンチマークの要約を信頼するのではなく、アーカイブされた生サンプルから報告されたすべてのパーセンタイル、MADs、および決定的信頼区間を再生成します。それは同様にカナリアの技術マニフェストを再読み込みし、すべてのアーカイブされたプライバシーサーフェスを独立して再スキャンするため、レポートはファイルの暗号化ダイジェストを再バインドした後に仕込まれた秘密のヒットを抑制することはできません。各シークレット専用の実行は、所有者専用の未フィルタリングのループバックPCAP、生のtcpdumpの標準エラー出力およびゼロドロップ統計、標準ポート技術マニフェスト、パックされた制限付きソースアーカイブ、およびすべてのピアの原子性観測を保持しなければなりません。最終検証者は、公開された要約を信頼するのではなく、アーカイブされたバイトからポートに結び付けられたパケット分割、ソース投影、およびベースラインから端末までの原子性チェックを再実行します。

アーカイブには、すべての必要なプライバシーサーフェスについて、正確な左右のファイルパス、種類、バイト長、および SHA-256 暗号学的ダイジェストを結び付ける標準的なペアトラフィックカウントおよび差分ペア技術マニフェストも含める必要があります。その宣言されたルートは、正確にペアになったアーカイブのインベントリを含まなければなりません。検証者は、通常の表面に対して、等しい全ファイルサイズと JSON の公開シェイプを必要とします。エントロピーを含む生ループバックキャプチャおよびパックされた制限付きソースアーカイブは明示的なサイズ例外です；代わりに、パケットリンクタイプとパケットごとの長さ、制限付きソースの識別、および固定形状の行長を比較します。すべての Torii リクエスト/レスポンス、公開/制限された P2P パケット、ブロック、クエリ、イベント、ログ、テレメトリトラフィックのカウントも一致する必要があります。パケット形状の変更、同サイズの構造的漏洩、偽の出所の主張、または、ペアになっていないファイルは、漏洩報告書とその暗号ハッシュを書き換えることで隠すことはできません。
